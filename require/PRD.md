## 1. 요약

DuoForge는 Codex와 Claude가 독립적으로 사고한 뒤 서로의 결과를 비평하고, 반박하고, 수정하도록 조율하여 개발 문서와 프로젝트 분석의 품질을 높이는 로컬 우선 토론 도구다.

v1은 사용자가 보유한 Codex 및 Claude 구독 기반 CLI 로그인을 사용할 수 있어야 하며, OpenAI·Anthropic API를 직접 호출하거나 사용자에게 API 키 입력을 요구하지 않는다. 사용자는 DuoForge 실행 전에 두 CLI를 미리 인증할 필요가 없다. 첫 실행 또는 인증 만료 시 DuoForge가 공식 공급자 CLI의 브라우저 로그인 절차를 안내하고, 두 구독 인증이 확인된 뒤에만 모델 호출을 시작한다. 두 AI를 직접 연결하는 대신 DuoForge가 고정된 입력 스냅샷, 구조화된 쟁점 원장, 라운드 장벽, 사용자 결정 게이트를 관리한다.

기본 사용자 경험은 명령과 옵션을 외우는 방식이 아니다. 사용자가 PowerShell 7에서 인수 없이 `duoforge`를 실행하면 방향키로 이동하고 `Enter`로 확정하는 대화형 메뉴가 열리고, 새 작업 생성, 파일·폴더 선택, Codex·Claude별 모델과 분석 깊이 선택, 진행 중인 작업 재개, 사용자 결정과 결과 열기를 현재 상태에 맞게 안내한다. 숫자·영문 단축키는 숙련 사용자를 위해 유지한다. Windows 파일·폴더 선택창을 기본으로 제공하되 드래그 앤 드롭·경로 붙여넣기·최근 경로와 기존 고급 CLI 명령도 함께 지원한다. 모델과 분석 깊이에는 묵시적 기본값을 사용하지 않으며 실제 실행마다 사용자가 각 공급자 값을 명시적으로 확정해야 한다.

v1 사용자 화면은 다음 네 가지 모드를 구분한다. 화면 번호는 표현 계층의 개념이며 기존 실행의 내부 모드 ID나 의미를 바꾸지 않는다.

1. **요구사항으로 공동 문서 만들기(`shared-document`)**: 간략한 요구사항 문서 C를 바탕으로 두 AI가 토론하여 공동 문서 C' 하나를 만든다.
2. **두 문서를 비교해 하나의 합의안 만들기(`document-merge`)**: 문서 A와 B를 동등한 출처로 검토하고 합의 문서 C 하나와 출처 추적표를 만든다.
3. **두 문서를 각각 개선하기(`dual-document`)**: 문서 A와 B의 계보를 유지한 채 두 공급자가 모두 두 문서를 검토하고 A'와 B'를 만든다.
4. **두 프로젝트 비교하기(`dual-project-audit`)**: 프로젝트 A와 B의 읽기 전용 비교를 수행하는 설계다. Windows 격리 게이트가 충족되지 않았으므로 메뉴에 비활성으로 표시하고 모델 호출 전에 차단한다.

문서 A/B는 파일명, 최초 작성자 또는 공급자 소유권이 아니라 한 실행 안에서 유지되는 안정적인 문서 계보 ID다. Codex와 Claude는 교체 가능한 검토자·응답자·편집자·합성자·검증자이며 어떤 문서도 영구 소유하지 않는다.

모든 모드는 기본 2라운드, 최대 3라운드로 제한한다. 중요한 미합의 사항은 AI가 임의로 타협하지 않고 쉬운 설명과 선택지를 갖춘 질문으로 변환하여 사용자에게 넘긴다. 사용자는 설명, 예시, 비용 비교 또는 실험 제안을 요청한 뒤 결정을 내리고 실행을 재개할 수 있다.

## 2. 문제 정의

단일 AI가 작성하거나 구현한 결과에는 다음과 같은 구조적 한계가 있다.

- 최초 전제와 초안의 방향에 스스로 고착될 수 있다.
- 누락된 요구사항, 반대 관점, 실패 시나리오를 충분히 탐색하지 못할 수 있다.
- 비평을 받더라도 무엇을 왜 수용하거나 거부했는지 추적하기 어렵다.
- 두 결과의 장점을 비교하고 선택적으로 흡수하는 과정이 비정형적이다.
- 해결되지 않은 기술적 쟁점을 사용자가 이해하고 결정할 수 있는 형태로 바꾸기 어렵다.
- 장시간 토론이 반복되거나 구독 사용량만 소비하면서 실질적인 개선이 멈출 수 있다.
- 프로젝트 비교 과정에서 모델이 원본 파일을 수정하거나 프로젝트 지시 파일을 명령으로 오인할 위험이 있다.

DuoForge는 두 모델의 독립성 자체보다 **입력 고정, 권한 격리, 대칭적 교차 검토, 판단 기록, 유한한 라운드, 사용자 결정권**을 제품의 핵심으로 삼아 이 문제를 해결한다.

## 3. 제품 목표

### 3.1 목표

- Codex와 Claude가 동일한 근거와 동일한 평가 기준으로 독립적으로 사고하게 한다.
- 두 AI가 상대 의견에 단순 동조하지 않고 구체적인 근거와 수정안을 제시하게 한다.
- 각 지적을 `수용`, `부분 수용`, `거부`, `근거 필요`, `사용자 결정 필요` 등으로 추적한다.
- 합리적인 불일치를 정상적인 결과로 보존한다.
- 기술 배경이 부족한 사용자도 쟁점과 선택지의 영향을 이해하고 결정할 수 있게 한다.
- 모든 입력, 비평, 반박, 반영, 사용자 결정과 최종 결과의 출처를 추적할 수 있게 한다.
- 실행이 중단되거나 한쪽 CLI가 실패해도 마지막 완료 체크포인트에서 재개할 수 있게 한다.
- 토론을 기본 2라운드, 최대 3라운드로 제한하고 최대 모델 호출 수를 실행 전에 알린다.
- 화면 모드 4에서 두 원본 프로젝트에 어떤 변경도 발생하지 않도록 기술적으로 격리하고 검증하며, 현재 격리 실패 상태에서는 모델 호출 전에 실패 폐쇄한다.
- DuoForge가 API 키를 직접 사용하거나 과금 인증 방식으로 자동 전환하지 않는다. 공급자 계정 수준의 사용량·크레딧 설정까지 통제한다고 약속하지 않는다.
- 공급자 CLI의 대화 세션이나 세션 재개 기능에 의존하지 않고 각 단계의 전체 문맥과 상태를 DuoForge가 관리한다.
- 일반 사용자는 내부 모드명, 실행 ID, 쟁점 ID와 세부 옵션을 외우지 않고 메뉴만으로 핵심 흐름을 완료할 수 있게 한다.
- 자동화와 재현성이 필요한 고급 사용자는 동일한 기능을 명시적 하위 명령과 옵션으로 실행할 수 있게 한다.
- 사용자가 사전에 공급자 CLI 인증 명령을 외우지 않아도 첫 실행에서 공식 로그인 절차를 완료하고 이후 저장된 인증을 재사용할 수 있게 한다.
- DuoForge가 이메일, 비밀번호, 인증 코드, 액세스 토큰 또는 API 키를 직접 입력받거나 저장하지 않게 한다.

### 3.2 v1 성공의 정의

사용자는 API 기반 멀티에이전트 서비스를 구축하거나 세부 명령 문법을 외우지 않고도 로컬 메뉴 또는 명시적 CLI 명령으로 실행을 시작하여 다음 중 하나를 얻을 수 있어야 한다.

- 컨셉 C에서 합의된 최종 개발 문서 C' 1개
- 문서 A/B에서 합의한 최종 문서 C 1개와 A/B 출처 추적표
- 서로 독립적으로 개선된 최종 개발 문서 A'/B' 2개
- 화면 모드 4가 활성화되기 전에는 격리 실패 이유와 필요한 안전 게이트

실행은 3라운드 안에 `완료`, `부분 완료`, `사용자 결정 대기` 또는 원인이 명시된 `재개 가능 오류` 상태에 도달해야 한다.

### 3.3 비목표

v1에서는 다음을 구현하지 않는다.

- Codex 또는 Claude API 직접 연동의 필수화
- 웹 서비스, 모바일 앱, 다중 사용자 협업
- Codex와 Claude 이외의 모델 공급자
- 무제한 자율 토론
- AI 응답 생성 도중의 실시간 개입
- 외부 웹 검색 및 자동 사실 검증
- Markdown 이외의 PDF, DOCX, HWP 직접 편집
- 완전한 Git 형상 관리 기능
- AI 판단의 사실성 또는 최적성 보장
- 두 AI가 반드시 같은 결론에 도달하도록 강제하는 기능
- 모드 3B의 코드 패치 제안 또는 생성
- 모드 3C의 코드 수정, 빌드, 테스트, 브랜치, 커밋, 푸시
- 프로젝트 의존성 설치, 개발 서버 실행, 애플리케이션 실행
- 상대 프로젝트 코드의 자동 복사 또는 병합
- 원격 서버나 CI에서의 완전 무인 운영
- 구독 한도 우회 또는 한도 도달 시 API 과금으로의 자동 전환
- 악성 프로젝트를 안전하게 실행하는 범용 보안 샌드박스
- 데스크톱 GUI와 모델 원시 응답 스트리밍. 단, 커서 이동·Enter 중심 CLI 메뉴, 표준 Windows 파일·폴더 선택창과 검증·커밋된 단계만 보여주는 고정형 TUI 진행판은 v1 범위에 포함한다.

## 4. 대상 사용자와 핵심 사용 사례

### 4.1 주요 사용자

- 아이디어를 PRD나 기술 문서로 구체화하려는 개인 개발자
- 서로 다른 설계안을 비교하는 기술 리더
- 기존 PRD의 누락과 위험을 교차 검증하려는 제품 담당자
- Codex와 Claude가 각각 만든 문서를 독립적으로 개선하려는 사용자
- 두 개의 프로토타입 또는 구현체를 비교하려는 개발자
- 기술적 결정을 내려야 하지만 해당 영역에 익숙하지 않은 사용자

### 4.2 핵심 사용자 스토리

- 아이디어 보유자로서, 짧은 프로젝트 설명만 제공하고 두 AI의 독립 검토를 거친 최종 PRD를 얻고 싶다.
- 제품 담당자로서, 먼저 작성된 초안에 전체 토론이 끌려가지 않기를 원한다.
- 제품 담당자로서, 서로 다른 문서 A와 B를 동등한 출처로 합의하여 새 문서 C 하나를 얻고 싶다.
- 개발자로서, 문서 A와 B를 억지로 같게 만들지 않고 각 계보의 장점을 유지한 개선본 두 개를 얻고 싶다.
- 기술 리더로서, 어떤 아이디어를 누가 제안했고 상대가 왜 수용하거나 거부했는지 확인하고 싶다.
- 비전문가로서, 기술적 미합의 사항을 쉬운 설명과 구체적인 예시로 이해한 뒤 결정하고 싶다.
- 사용자로서, 결정을 잘 모를 때 권고안, 안전한 기본값 또는 검증 실험을 제안받고 싶다.
- 사용자로서, 프로그램 또는 한쪽 CLI가 중단되어도 처음부터 다시 시작하지 않고 이어가고 싶다.
- 프로젝트 소유자로서, 두 프로젝트를 비교하는 동안 어느 쪽 코드도 변경되지 않기를 원한다.
- 개발자로서, 프로젝트 비교 보고서의 주장을 실제 파일과 심볼 위치로 검증하고 싶다.
- 사용자로서, 토론이 끝없이 반복되지 않고 최대 3라운드 안에 결과 또는 결정 질문을 받고 싶다.
- 처음 사용하는 사용자로서, `duoforge` 하나만 실행하고 작업 종류와 입력 경로를 선택하여 안전한 기본값으로 시작하고 싶다.
- Windows 사용자로서, 긴 한글·공백 경로를 직접 입력하지 않고 파일·폴더 선택창이나 드래그 앤 드롭으로 고르고 싶다.
- 다시 방문한 사용자로서, 실행 ID를 기억하지 않고 진행 중인 작업과 다음 동작을 바로 확인하고 싶다.
- 고급 사용자로서, 메뉴와 동일한 동작을 명시적 CLI 명령으로 자동화하고 싶다.
- 처음 사용하는 사용자로서, Codex와 Claude에 미리 로그인하지 않았더라도 DuoForge가 공식 로그인 절차를 순서대로 안내한 뒤 작업을 시작해 주길 원한다.

## 5. 핵심 제품 원칙

1. **독립성 우선**  
   최초 제안과 최초 분석은 상대 결과를 보지 않은 상태에서 생성한다.

2. **동일 스냅샷 원칙**  
   한 라운드의 양쪽 검토는 정확히 같은 시점의 입력 스냅샷을 사용한다.

3. **라운드 장벽**  
   양쪽 검토가 모두 완료되기 전에는 반박이나 다음 버전 생성을 시작하지 않는다.

4. **문서 계보와 작업자 분리**
   문서 A/B는 실행 동안 안정적인 계보로 유지하고 공급자와 영구 결합하지 않는다. 단계의 `performedBy`는 감사용 작업 할당일 뿐 문서 소유권이 아니다. 프로젝트 비교 모드에서는 어느 프로젝트도 갱신하지 않는다.

5. **근거 있는 불일치 허용**  
   합의 자체보다 근거와 선택의 결과를 중요하게 본다. 타당한 거부와 미합의는 정상 결과다.

6. **사용자 최종 결정권**  
   제품 범위, 비용, 일정, 위험 선호처럼 정답이 없는 쟁점은 사용자가 결정한다.

7. **설명 우선**  
   사용자가 이해하지 못한 상태에서 선택을 강요하지 않는다.

8. **추적성**  
   모든 중요 지적에는 고유 ID, 근거, 판단, 이유, 반영 위치와 상태 이력이 있어야 한다.

9. **유한한 실행**  
   기본 2라운드, 최대 3라운드를 강제하고 재시도와 설명 호출도 별도 예산으로 제한한다.

10. **로컬 우선과 명시적 전송**  
    실행 기록은 로컬에 저장하되, 선택된 입력 내용이 두 모델 공급자에게 전송될 수 있음을 실행 전에 알린다.

11. **메뉴 우선, 명령어 병행**  
    사람에게는 상태 기반 메뉴와 안전한 기본값을 제공하고, 자동화에는 동일한 도메인 기능을 호출하는 명시적 CLI를 제공한다. 메뉴는 별도 업무 로직을 복제하지 않는다.

## 6. 용어 정의

| 용어 | 정의 |
|---|---|
| 실행(`run`) | 하나의 입력과 설정으로 시작하여 최종 산출물 또는 중단 상태에 이르는 전체 작업 |
| 단계(`stage`) | 초안, 검토, 반박, 수정, 질문 생성처럼 재개 가능한 최소 작업 단위 |
| 라운드(`round`) | 동일 스냅샷에 대한 양쪽 검토와 그에 대한 반박·수정이 완료되는 논리적 단위 |
| 스냅샷 | 실행 또는 라운드 시작 시점의 변경 불가능한 입력 사본과 해시 목록 |
| 컨텍스트 팩 | 원본 경로를 직접 모델 작업 폴더로 열지 않고 분석할 수 있도록 정규화한 텍스트 입력 묶음 |
| 쟁점(`issue`) | 한쪽이 제기한 구체적인 결함, 제안, 질문 또는 불일치 |
| 쟁점 원장 | 쟁점의 고유 ID와 전체 상태 변경을 보존하는 기계 판독 가능 기록 |
| 결정 게이트 | AI가 임의로 결정할 수 없는 쟁점을 사용자에게 설명하고 답변을 기다리는 체크포인트 |
| 채택 이력 | 상대 아이디어를 어느 결과에 왜 반영했는지 기록한 목록 |
| 문서 계보 ID | 한 실행 안에서 입력과 후속 버전을 연결하는 `brief`, `A`, `B`, `merged` 식별자. 작성자나 공급자 소유권을 뜻하지 않음 |
| 공급자 작업자 | Codex 또는 Claude처럼 단계별 검토·응답·편집·합성·검증을 수행하는 교체 가능한 실행 주체 |
| `workflow-v1` | `workflowVersion`이 없는 기존 실행에 적용하는 레거시 단계·역할·파일·프롬프트 의미 |
| `workflow-v2` | 문서 계보와 공급자를 분리한 신규 실행 계약 |
| 레거시 입력 어댑터 | 기존 `CodexDocument/ClaudeDocument`, `--codex/--claude` 입력을 읽기 경계에서 A/B 정규형으로 변환하되 저장 원본은 바꾸지 않는 계층 |
| 부분 완료 | 입력 커버리지 부족 등으로 제한된 결론만 낼 수 있는 완료 상태 |
| 대화형 메뉴 | 인수 없는 `duoforge`에서 시작하며 숫자·문자 선택으로 작업 생성, 재개, 결정과 결과 열기를 안내하는 CLI 표현 계층 |

## 7. 지원 입력과 문서 유형

### 7.1 문서 입력

- v1의 기본 문서 형식은 UTF-8 Markdown이다.
- 기본 평가표를 제공하는 문서 유형은 다음과 같다.
  - PRD
  - 아키텍처 문서
  - 구현 계획
  - 기술 의사결정 기록(ADR)
- 사용자 정의 Markdown도 입력할 수 있으나 전용 평가표는 보장하지 않는다.
- 모드 1은 컨셉 또는 `brief` 하나, 모드 2·3은 주요 문서 A/B 두 개와 각 문서 폴더의 보조 Markdown, 모드 4는 프로젝트 A/B 한 쌍을 대상으로 한다.

### 7.2 프로젝트 입력

- 프로젝트 폴더 두 개와 두 프로젝트에 공통으로 적용할 목표, 요구사항 또는 평가 기준을 받아야 한다.
- 공통 기준이 없다면 DuoForge가 가정안을 만들 수 있지만, 사용자가 확인하기 전에는 사실로 취급하지 않는다.
- 텍스트 기반 소스, 설정, 테스트 및 문서 파일을 대상으로 정적 분석한다.
- `.git`, 의존성, 캐시, 빌드 결과물, 대형 바이너리, 미디어와 비밀정보 파일은 기본 제외한다.
- 정션과 심볼릭 링크는 기본적으로 따라가지 않는다.

### 7.3 v1 기본 용량 정책

- 문서 모드의 입력 Markdown은 파일당 최대 2 MiB를 기본값으로 한다.
- 프로젝트 모드의 인벤토리는 전체 경로를 기록하되, 모델 분석 대상으로 포함하는 텍스트는 프로젝트당 최대 5,000개 파일과 합계 1 MiB를 기본값으로 한다.
- 개별 텍스트 파일은 512 KiB를 넘으면 기본 제외하고 이유를 기록한다.
- 제한값은 설정으로 변경할 수 있지만 실행 전 예상 전송량과 호출 계획을 다시 확인해야 한다.
- 한도를 넘은 입력을 앞부분만 조용히 자르지 않는다. 사용자가 포함 경로를 좁히거나 `부분 분석`으로 진행하도록 선택하게 한다.
- 여러 배치로 요약하더라도 최종 주장에는 원본 상대 경로와 근거 위치를 유지한다.
- 신규 대용량 Markdown 실행은 `context-plan.schemaVersion=2`의 결정론적 구조 맵을 사용한다. 제목·제목 경로, 서문, 완결된 문단·목록·표·fenced code를 의미 경계로 우선 보존하고, 한 의미 단위가 호출 상한을 넘을 때만 문단·줄·UTF-8 안전 바이트 순서로 폴백한다.
- 분할과 패킹은 XML escape 뒤 실제 전송 바이트를 함께 계산한다. 브리지와 문서 지도를 최소화해도 맞지 않는 CORE는 UTF-8 경계에서 더 나누고, 최소 봉투도 불가능한 경우 첫 공급자 호출 전에 실패한다.
- 각 문맥 팩은 `DOCUMENT_MAP`, `BEFORE`, `CORE`, `AFTER`를 구분한다. 지도와 앞뒤 연결 범위는 위치 이해 전용 `context-only`이고 `CORE` 원본 범위만 사실 분석·인용·쟁점 근거가 될 수 있다.
- 기존 context-plan schema 1과 workflow-v1·초기 workflow-v2 저장 실행은 신규 분할기로 재생성하거나 마이그레이션하지 않는다.

## 8. 모드 1: 공동 합의 문서

### 8.1 목적

사용자의 프로젝트 설명을 출발점으로 Codex와 Claude가 독립 초안을 작성하고 상호 비평한 뒤 하나의 최종 개발 문서를 만든다.

### 8.2 입력

- 프로젝트 설명 또는 `brief.md`
- 문서 유형
- 선택적 문서 템플릿
- 선택적 제약 조건과 우선순위
- 최대 라운드 수: 2 또는 3, 기본 2. 최소 정상 토론 라운드는 2
- 첫 합성 담당: `codex`, `claude` 또는 `alternate`, 기본 `alternate`

### 8.3 처리 흐름

#### 라운드 1

1. 입력을 검증하고 불변 스냅샷을 만든다.
2. Codex와 Claude가 서로의 결과를 보지 않고 독립 초안을 작성한다.
3. 두 초안이 모두 완료된 후에만 서로에게 공개한다.
4. Codex는 Claude 초안을, Claude는 Codex 초안을 동일한 평가표로 비평한다.
5. 양쪽 비평이 모두 끝난 후 각 초안 작성자가 자신이 받은 지적에 수용, 부분 수용 또는 근거를 갖춘 반박으로 응답한다.
6. 공통점, 차이점, 상충점과 채택 후보를 쟁점 원장에 등록한다.
7. 지정된 합성 담당이 두 초안, 양쪽 비평과 작성자 반박을 바탕으로 공동 문서 v1을 만든다.

#### 라운드 2~3

1. 공동 문서의 현재 버전을 고정한다.
2. Codex와 Claude가 각각 독립적으로 공동 문서를 검토한다.
3. 양쪽 검토가 모두 끝난 후 각 AI가 상대의 새 지적에 한 번씩 응답한다.
4. 다음 합성 담당이 양쪽 판단을 보존한 채 쟁점별 처리 결정을 기록한다.
5. 합성 담당은 수용한 내용을 반영하여 공동 문서의 다음 버전을 만든다.
6. 합성 담당을 직전 라운드와 반대로 교대한다.
7. 조기 종료 또는 사용자 결정 게이트 조건을 평가한다.

#### 모드 1 종료

1. 직전 합성 담당이 아닌 AI가 최종 검증을 수행한다.
2. 열린 Critical 쟁점과 사용자 결정이 필요한 Major 쟁점을 숨긴 채 완료 처리할 수 없다.
3. 최종 검증에서 새 Critical 또는 Major 쟁점이 발견되면 남은 라운드에서 수정하거나 사용자 결정 게이트로 보낸다.
4. 필요한 사용자 결정을 반영한 뒤 최종 공동 문서와 감사 기록을 출력한다.

### 8.4 필수 산출물

```text
final/
├─ PRD.md 또는 선택한 문서 유형의 최종 파일
├─ DECISIONS.md
├─ OPEN_QUESTIONS.md
└─ DEBATE_SUMMARY.md

rounds/
├─ 최초 Codex 초안
├─ 최초 Claude 초안
├─ 라운드별 검토
├─ 라운드별 반박
└─ 공동 문서 버전
```

### 8.5 모드 1 수용 기준

- 최초 초안 두 개는 양쪽 생성이 모두 완료되기 전까지 상대에게 공개되지 않는다.
- 동일한 평가표로 교차 검토한다.
- 합성 담당이 라운드마다 교대된 기록이 남는다.
- 최종 공동 문서 1개, 토론 요약, 결정 기록과 미해결 질문 목록이 생성된다.
- 최종 문서는 직전 합성 담당이 아닌 AI의 검증을 거친다.

## 9. 모드 2: 두 문서를 하나로 합의

### 9.1 목적

서로 다른 문서 A와 B를 어느 공급자의 소유물이나 기준본으로 취급하지 않고 동등한 출처로 검토하여 새 합의 문서 C 하나를 만든다.

### 9.2 입력

- 원본 Markdown 문서 A와 B
- A와 B가 들어 있는 서로 분리되고 중첩되지 않은 폴더
- 각 폴더의 나머지 Markdown. 각각 `document-a-context`, `document-b-context` 역할의 읽기 전용 보조 문맥으로 자동 포함한다.
- 선택적 추가 A/B 보조 Markdown 폴더
- 문서 유형, 선택적 공통 요구사항과 평가 기준
- 최대 라운드 수: 2 또는 3, 기본 2. 최소 정상 토론 라운드는 2

### 9.3 처리 흐름

#### 라운드 1

1. 문서 A/B와 각 보조 문맥을 같은 시점의 불변 스냅샷으로 고정한다.
2. Codex와 Claude가 서로의 결과를 보지 않고 같은 A/B 스냅샷으로 완성된 병합 후보 C를 각각 작성한다. 단계 유형은 `independent-merge-draft`다.
3. 두 후보가 모두 완료된 뒤에만 상대 후보를 공개하고 같은 평가표로 교차 검토한다.
4. 각 공급자가 받은 지적에 응답한다.
5. 지정된 합성 담당이 A/B 출처, 두 후보, 검토와 응답을 바탕으로 공동 문서 C v1을 만든다.
6. 합성 결과에는 A/B 항목별 `ADOPTED`, `PARTIALLY_ADOPTED`, `REJECTED`, `UNRESOLVED`, 이유와 반영 위치를 기록한다.

#### 라운드 2~3

1. 현재 C와 A/B 출처 추적표를 동시에 고정한다.
2. 두 공급자가 같은 스냅샷을 독립 검토한다.
3. 양쪽 검토가 완료된 뒤 상호 응답한다.
4. 합성 담당을 직전 라운드와 반대로 교대하여 C의 다음 버전과 출처 추적표를 갱신한다.
5. 종료 조건과 사용자 결정 게이트를 평가한다.

#### 종료

1. 마지막 합성 담당이 아닌 공급자가 `document-validation`을 수행한다.
2. 열린 Critical 쟁점과 사용자 결정이 필요한 Major 쟁점을 숨긴 채 완료하지 않는다.
3. 최종 합의 문서 C와 출처 추적표, 토론 요약, 사용자 결정과 열린 질문을 출력한다.

### 9.4 문서 계보와 출처 규칙

- 원본 A/B는 변경하거나 덮어쓰지 않는다.
- 어느 공급자도 A 또는 B의 소유자가 아니다.
- A/B 중 하나를 묵시적인 기준본이나 우선 출처로 지정하지 않는다.
- `sourceDocumentId`와 `proposedByProvider`를 별도 필드로 기록한다.
- 합성 담당의 `performedBy`는 작업 할당일 뿐 결과 C의 소유권을 뜻하지 않는다.
- 같은 폴더, 중첩 폴더, 링크 탈출 또는 입력 내부 결과 루트는 모델 호출 전에 차단한다.

### 9.5 필수 산출물

```text
final/
├─ PRD.md 또는 선택한 문서 유형의 최종 파일
├─ source-trace.md
├─ DECISIONS.md
├─ OPEN_QUESTIONS.md
└─ DEBATE_SUMMARY.md
```

### 9.6 모드 2 수용 기준

- 두 병합 후보는 서로를 보지 않고 같은 A/B 스냅샷을 사용한다.
- A/B를 동등한 출처로 취급하며 출처별 채택 상태, 이유와 반영 위치를 확인할 수 있다.
- 마지막 합성자가 아닌 공급자가 최종 검증한다.
- 원본 A/B의 실행 전후 해시가 같다.
- 최종 합의 문서 하나와 출처 추적표가 생성된다.

## 10. 모드 3: 두 문서를 각각 개선

### 10.1 목적

문서 A와 B의 정체성과 계보를 유지하면서 두 공급자가 모두 두 문서를 검토하고 라운드마다 교대하여 A'와 B'를 만든다. 특정 공급자가 특정 문서를 영구 소유하지 않는다.

### 10.2 입력

- 원본 Markdown 문서 A와 B
- 각 원본이 들어 있는 서로 분리되고 중첩되지 않은 폴더
- 각 폴더의 나머지 Markdown과 선택적 추가 보조 Markdown 폴더
- 각 문서의 목적, 문서 유형, 선택적 공통 요구사항과 평가 기준
- 최대 라운드 수: 2 또는 3, 기본 2. 최소 정상 토론 라운드는 2

### 10.3 처리 흐름

각 라운드는 다음 장벽을 가진다.

1. 현재 A와 B의 불변 스냅샷을 동시에 만든다.
2. Codex와 Claude가 각각 A와 B 모두를 같은 평가표로 검토하고 모든 쟁점을 `targetDocumentId=A|B`로 분류한다. 단계 유형은 `document-review`다.
3. 양쪽 검토가 모두 완료된 뒤 서로의 쟁점에 `review-response`로 응답한다.
4. A와 B에 대해 각각 한 번씩 `document-revision`을 수행한다. 두 편집 단계는 양쪽 응답에 의존한다.
5. 편집 담당을 라운드마다 교대한다. 예를 들어 R1은 Codex→A, Claude→B이고 R2는 Claude→A, Codex→B다. 이는 작업 할당이지 소유권이 아니다.
6. A/B 수정본이 모두 검증·커밋된 뒤에만 다음 라운드의 새 스냅샷을 만든다.
7. 종료 조건을 평가하고 필요한 경우 사용자 결정 게이트로 이동한다.
8. 마지막 라운드 뒤에는 각 문서를 마지막 편집자가 아닌 공급자가 `document-validation`으로 검증한다.

### 10.4 문서 계보와 편집 규칙

- 원본 A/B는 실행 종료까지 변경하거나 덮어쓰지 않는다.
- 두 주요 문서의 부모 폴더는 서로 달라야 하며 같거나 중첩되면 모델 호출 전에 차단한다.
- 각 주요 문서 폴더의 나머지 Markdown은 해당 문서 계보의 읽기 전용 보조 문맥으로만 포함한다.
- 공급자는 어떤 문서도 영구 소유하지 않으며 라운드별 작업 할당 외에는 고정 결합하지 않는다.
- 사용자 결정은 A/B 모두에 구속력 있는 공통 제약으로 전달한다.
- 서로 다른 타당한 대안은 유지하며 A'와 B'를 억지로 같게 만들지 않는다.

### 10.5 쟁점 판단과 생명주기

신규 워크플로는 문서별 편집 판단(`editorialDecisions`), 검토자 평가(`reviewerVerdicts`), 쟁점 생명주기(`resolutionStatus`)를 별도 축으로 저장한다. `sourceDocumentId`와 `proposedByProvider`도 분리한다. `ownerDecisions`는 `workflow-v1` 레거시 결과를 읽을 때만 허용한다.

| 편집 판단 | 의미 | 필수 조건 |
|---|---|---|
| `UNREVIEWED` | 아직 판단하지 않음 | 최초 등록 상태 |
| `ACCEPTED` | 전부 수용 | 대상 문서와 반영 위치 필요 |
| `PARTIALLY_ACCEPTED` | 일부 수용 | 수용·거부 범위와 반영 위치 필요 |
| `REJECTED` | 거부 | 구체적인 이유 또는 근거 필요 |
| `DEFERRED` | 의도적으로 보류 | 보류 이유와 재검토 조건 필요 |

| 검토자 평가 | 의미 | 필수 조건 |
|---|---|---|
| `AGREES` | 편집 판단과 이유에 동의 | 확인한 근거 필요 |
| `PARTIALLY_AGREES` | 일부만 동의 | 동의·불일치 범위 필요 |
| `DISAGREES` | 편집 판단을 반대 | 반대 이유와 대안 필요 |
| `UNVERIFIABLE` | 현재 근거로 평가 불가 | 필요한 근거 또는 사용자 질문 필요 |

쟁점 생명주기는 `OPEN`, `AWAITING_EVIDENCE`, `AWAITING_USER`, `DEFERRED`, `RESOLVED`, `SUPERSEDED`를 사용하며 상태 이력을 덮어쓰지 않는다. 합리적 불일치는 편집 판단과 `reviewerVerdict=DISAGREES`의 근거를 보존하여 종료할 수 있다.

### 10.6 필수 산출물

```text
final/
├─ document-A-final.md
├─ document-B-final.md
├─ comparison.md
├─ adoption-log.md
└─ OPEN_QUESTIONS.md
```

`adoption-log.md`는 쟁점 ID, `sourceDocumentId`, `proposedByProvider`, 대상 문서, 수용 상태, 이유, 반영 위치와 라운드를 포함한다.

### 10.7 모드 3 수용 기준

- 한 라운드의 두 공급자는 같은 A/B 버전을 사용하고 A/B 모두를 검토한다.
- 편집 담당은 라운드마다 교대하며 특정 문서와 영구 결합되지 않는다.
- A/B 두 수정본이 모두 커밋되기 전에 다음 라운드가 시작되지 않는다.
- 모든 Critical 및 Major 지적에 대상 문서, 상태와 이유가 존재한다.
- 원본 A/B의 실행 전후 해시가 같다.
- A'/B'와 비교표, 문서별 채택 이력이 모두 생성된다.

## 11. 모드 4: 독립 프로젝트 읽기 전용 비교

### 11.1 목적

별도로 구현된 두 프로젝트를 변경하지 않고 분석하여 기능 구현 상태, 구조, 강점, 결함, 위험, 근거 부족과 상대 프로젝트에서 도입할 수 있는 아이디어를 비교한다.

모드 4의 결과 설계는 코드 변경이 아니라 **근거 기반 비교 보고서와 프로젝트별 개선 계획**이다. 현재는 메뉴에 `[4] 두 프로젝트 비교하기 — 비활성화`로 표시하며 선택하면 `DF-PREFLIGHT-3A-ISOLATION`과 실패 이유를 안내하고 입력 전송이나 모델 호출 전에 종료한다.

### 11.2 입력

- 프로젝트 A 폴더 절대 경로
- 프로젝트 B 폴더 절대 경로
- 공통 목표, 원래 요구사항 또는 평가 기준
- 선택적 제외 경로
- 선택적 추가 평가 기준
- 최대 라운드 수: 2 또는 3, 기본 2. 최소 정상 토론 라운드는 2

### 11.3 강제 읽기 전용 경계

- 모델 프로세스에 원본 프로젝트의 쓰기 권한을 주지 않는다.
- 모델을 원본 프로젝트 폴더에서 실행하지 않는다.
- 오케스트레이터가 원본을 읽어 별도 실행 폴더에 정규화된 컨텍스트 팩을 만든다.
- `AGENTS.md`, `CLAUDE.md`, README, 코드 주석 및 기타 입력 내 지시문은 모두 분석 대상 데이터로만 취급한다.
- 특별한 이름의 지시 파일이 모델 런타임에 자동 로드되지 않도록 원본 파일명을 그대로 모델 작업 디렉터리에 배치하지 않는다.
- 모델이 생성한 명령, 파일 경로 또는 후속 동작은 실행하지 않는다.
- 코드 패치, 포맷팅, 의존성 설치, Git 변경, 빌드, 테스트, 개발 서버 및 애플리케이션 실행을 금지한다.
- 모든 산출물은 두 프로젝트 외부의 DuoForge 실행 폴더에만 저장한다.
- 입력 폴더끼리 중첩되거나 출력 폴더가 입력 폴더 내부이면 실행을 거부한다.
- 정션 또는 심볼릭 링크가 허용 범위 밖을 가리키면 해당 링크를 제외하고 경고한다.
- 실행 전후에 오케스트레이터가 직접 읽은 파일 인벤토리와 SHA-256을 비교한다. 3A에서는 Git 프로세스도 실행하지 않는다.
- 원본 변경이 감지되면 실행을 성공으로 표시하지 않고 안전 실패로 종료한다.

> **출시 차단 조건:** 대상 프로젝트를 모델 프로세스로부터 쓰기·범위 밖 읽기·자식 프로세스 실행에서 격리하고 프로젝트 내부 자동 지시 파일이 DuoForge 규칙보다 우선 적용되지 않음을 검증할 수 없으면 모드 4를 활성화하지 않는다. `docs/3A_ISOLATION_SPIKE.md`의 현재 실패 판정을 UI 선택이나 사용자 확인으로 우회하지 않는다.

#### 공급자 실행 계약

각 공급자 어댑터는 지원 CLI 버전별로 다음 계약을 기능 검사와 격리 픽스처 테스트로 증명해야 한다. 하나라도 증명하지 못하면 해당 어댑터로 모드 4를 실행하지 않는다.

- 모델 프로세스의 작업 폴더는 두 입력 프로젝트와 그 상위 트리 밖에 있는 새 격리 폴더다.
- 모드 4는 사용자가 명시한 `--workspace` 절대 경로를 요구하며, 이 경로가 두 프로젝트 내부이거나 서로 중첩되면 거부한다.
- 오케스트레이터가 컨텍스트 팩을 배치별 표준입력으로 전달하고 모델의 파일 접근 도구는 기본 0개다.
- 사용자·프로젝트 설정, 자동 지시, MCP, 훅, 플러그인, 스킬, 자동 메모리, 웹, 브라우저와 셸 도구를 비활성화하거나 빈 격리 설정으로 대체한다.
- 권한 우회 없이 비대화형·임시 세션·읽기 전용 실행을 사용한다.
- 자식 프로세스 환경은 인증과 네트워크 연결에 꼭 필요한 허용 목록만 전달하고 프로젝트 임의 환경 변수는 전달하지 않는다.
- 결과는 공급자별 검증된 JSON 스키마를 통과해야 하며 모델 출력은 다음 명령이나 파일 경로 결정에 직접 사용하지 않는다.
- 위 계약의 구체적인 CLI 플래그와 지원 버전은 어댑터 매니페스트에 기록하고 `doctor`가 실행 시점에 검증한다.

### 11.4 컨텍스트 팩

오케스트레이터는 서로 다른 두 인벤토리를 만든다.

- **비공개 무결성 인벤토리**: 실행 전후 비교를 위해 전체 정규화 경로, 크기와 해시를 로컬에만 보관하며 모델에 보내지 않는다.
- **모델 공개용 정제 인벤토리**: 포함된 파일의 안전한 별칭과 필요한 메타데이터만 담고, 제외된 비밀 파일은 이름을 노출하지 않은 통계와 제외 사유 범주만 제공한다.

컨텍스트 팩은 다음 정보를 포함한다.

- 정제된 상대 경로 별칭, 크기, 해시와 파일 유형
- 포함한 텍스트 파일과 제외한 파일 목록
- 각 제외 이유
- 원본 경로와 정규화된 컨텍스트 파일의 매핑
- 분석한 바이트 수와 전체 텍스트 바이트 수
- 파일별 줄 번호 매핑
- 공통 요구사항 및 평가표

컨텍스트 팩의 파일은 `F000001.txt`처럼 안전한 내부 이름을 사용하고, 원본 경로는 별도 매니페스트로 연결한다. 입력 내용은 명시적인 데이터 구획 안에서 모델에 전달한다.

### 11.5 기본 제외 규칙

- `.git`
- `.env`, `*.pem`, `*.key`, 인증서, 개인키, 자격증명 파일
- `node_modules`, `.venv`, `venv`, 패키지 캐시
- `dist`, `build`, `coverage`, 임시 파일과 캐시
- 실행 파일, 압축 파일, 이미지, 영상, 오디오와 기타 바이너리
- 사용자가 지정한 제외 패턴
- 프로젝트 외부로 연결되는 정션과 심볼릭 링크

비밀정보로 의심되는 값은 프롬프트, 로그, 컨텍스트 팩 또는 최종 문서에 원문으로 남기지 않는다. 모델 응답을 저장할 때도 비밀정보 필터를 다시 적용하며, 필터링 전 수신 바이트의 해시와 필터링된 보존본만 저장한다. 휴리스틱 탐지는 완전한 비밀정보 차단을 보장하지 않으므로 실행 전 각 공급자에게 전송될 파일 목록과 제외 목록의 요약을 사용자가 검토해야 한다.

### 11.6 비교 기준

- 공통 요구사항 대비 기능 커버리지
- 구현된 기능과 누락된 기능
- 프로젝트 구조와 아키텍처
- 모듈 경계, 책임 분리와 데이터 흐름
- 오류 처리와 예외 상황
- 보안 및 개인정보 위험
- 테스트 자산의 존재와 검증 가능성
- 운영, 배포와 관찰 가능성
- 성능 및 확장성 위험
- 유지보수성, 복잡성 및 문서화 수준
- 상대 프로젝트에서 도입할 만한 아이디어

테스트 파일이 존재하는 것과 테스트가 실제 통과한 것을 구분해야 한다. 모드 4는 테스트를 실행하지 않으므로 결과에 `테스트 미실행`을 명시한다.

### 11.7 처리 흐름

#### 사전 검사

1. 두 입력 경로를 절대 경로로 정규화한다.
2. 동일 경로, 중첩 경로, 출력 경로 중첩과 링크 탈출을 차단한다.
3. 두 CLI의 설치, 버전, 로그인 상태와 활성 인증 방식을 확인한다.
4. 입력 인벤토리와 제외 목록을 생성한다.
5. 사용자에게 전송 범위, 읽기 전용 제한과 예상 최대 호출 수를 보여준다.
6. 원본 무결성 기준선을 기록한다.

#### 분석과 토론

1. 안전한 컨텍스트 팩 두 개를 만든다.
2. Codex와 Claude가 같은 두 컨텍스트 팩과 같은 평가표로 양쪽 프로젝트를 각각 독립 평가한다.
3. 양쪽 최초 분석이 모두 끝난 후에만 상대 분석을 공개한다.
4. 각 AI가 상대 분석의 누락, 과장, 편향과 근거 부족을 비평한다.
5. 각 AI가 지적을 수용, 부분 수용, 거부 또는 근거 필요로 분류하고 자신의 분석을 갱신한다.
6. 추가 라운드가 설정되면 갱신된 동일 시점 분석을 다시 고정하여 반복한다.
7. 근거 부족이나 사용자 선호가 필요한 쟁점을 결정 게이트로 보낸다.

#### 모드 4 종료

1. 프로젝트별 개선 계획과 종합 비교표를 만든다.
2. 각 코드 관련 주장에 상대 경로, 줄 번호 또는 심볼 근거를 연결한다.
3. 근거가 없으면 `검증되지 않은 가정`으로 표시한다.
4. 분석 커버리지를 계산한다.
5. 커버리지가 기준보다 낮으면 `부분 완료`로 표시하고 프로젝트 전체에 대한 단정적 승자 판정을 금지한다.
6. 원본 무결성을 다시 검증하고 결과를 기록한다.

#### 커버리지 판정

안전상 강제 제외와 사용자가 명시적으로 제외한 경로를 뺀 파일을 `분석 가능 대상`으로 정의한다. 용량 또는 호출 예산 때문에 제외된 파일은 분모에서 빼지 않는다. 네 지표는 `공급자 × 프로젝트` 조합별로 각각 계산하며, 한쪽 공급자의 높은 커버리지로 다른 쪽의 누락을 상쇄하지 않는다.

| 지표 | 계산 | `COMPLETED` 기준 |
|---|---|---|
| 텍스트 파일 커버리지 | 실제 분석 파일 수 / 분석 가능 텍스트 파일 수 | 90% 이상 |
| 텍스트 바이트 커버리지 | 실제 분석 바이트 / 분석 가능 텍스트 바이트 | 90% 이상 |
| 필수 자산 커버리지 | 요구사항, 진입점, 핵심 설정과 핵심 모듈 중 분석한 항목 / 탐지된 필수 항목 | 100% |
| 요구사항 근거 커버리지 | 구현 근거 또는 `근거를 찾지 못함` 판정을 가진 요구사항 / 전체 공통 요구사항 | 100% |

어느 `공급자 × 프로젝트` 조합에서든 한 지표라도 기준을 충족하지 못하면 `COMPLETED_PARTIAL`로 표시한다. 결과에는 조합별 네 지표를 모두 별도로 보여주며 파일 수나 바이트 수 하나만으로 완전성을 주장하지 않는다.

### 11.8 필수 산출물

```text
final/
├─ project-comparison.md
├─ project-A-improvement-plan.md
├─ project-B-improvement-plan.md
├─ implementation-matrix.md
├─ evidence-index.md
├─ coverage-report.md
├─ integrity-report.md
└─ OPEN_QUESTIONS.md
```

### 11.9 모드 4 수용 기준

- 원본 프로젝트 내부에 새 파일, 수정 파일 또는 삭제 파일이 없다.
- 원본 프로젝트에서 어떤 프로젝트 명령도 실행되지 않는다.
- 분석 전후 무결성 보고서가 생성되고 두 기준선이 일치한다.
- 코드 관련 모든 Critical 및 Major 주장에 파일, 줄 또는 심볼 근거가 있거나 `근거 없음`으로 표시된다.
- 테스트 자산의 존재를 테스트 통과로 표현하지 않는다.
- 모든 결과물이 두 원본 프로젝트 외부에 생성된다.
- 패치, 브랜치, 커밋 또는 코드 변경 산출물이 생성되지 않는다.
- 양쪽 프로젝트의 커버리지와 제외 파일이 명시된다.
- 현재 격리 게이트가 닫힌 동안에는 위 분석 단계 대신 `DF-PREFLIGHT-3A-ISOLATION`으로 모델 호출 전에 차단된다.

## 12. 공통 토론 프로토콜

### 12.1 라운드 정책

- 기본 라운드 수는 2이며 사용자가 3으로 지정할 수 있다.
- 정상적인 조기 수렴 판정은 최소 2라운드를 완료한 뒤에만 수행한다. 사전 검사 실패, 사용자 결정을 요구하는 차단 입력, 인증·한도 오류와 사용자 중단은 예외다.
- 자동 실행은 3라운드를 초과할 수 없다.
- 설명 요청과 사용자 답변은 토론 라운드에 포함하지 않는다.
- 재시도는 라운드에 포함하지 않지만 모델 호출 예산에는 포함한다.
- 전송 오류, 일시적 오류 또는 구조화 결과 오류는 단계당 최대 1회만 재시도한다. 현재 입력 세대의 허용 재시도를 모두 사용하면 해당 단계는 `FAILED_STAGE`로 종료하며 일반 `resume` 대상으로 표시하지 않는다.
- 한쪽 호출이 실패하면 상대 결과만으로 라운드를 완료 처리하지 않는다.
- 완료된 상대 단계는 재개 시 다시 실행하지 않는다.
- 같은 주장의 표현만 바꾼 반복은 새로운 쟁점으로 만들지 않는다.

| 모드 | 라운드 1 | 라운드 2~3 |
|---|---|---|
| 모드 1 공동 문서 | 블라인드 초안 2개 → 교차 비평 → 작성자별 응답 → 공동 문서 합성 | 공동 문서 고정 → 양쪽 비평 → 양쪽 응답 → 교대 합성 |
| 모드 2 문서 합의 | A/B 고정 → 독립 병합 후보 2개 → 교차 비평 → 양쪽 응답 → C 합성 | C와 A/B 출처표 고정 → 양쪽 검토·응답 → 교대 합성 |
| 모드 3 문서별 개선 | A/B 고정 → 두 공급자의 A/B 전체 검토 → 양쪽 응답 → A/B 각각 개정 | 직전 A/B를 동시 고정 → 편집 담당 교대 → A/B 개정 완료 장벽 |
| 모드 4 프로젝트 비교 | 격리 게이트 미충족으로 모델 호출 전 차단 | 실행하지 않음 |

### 12.2 종료 조건

다음 중 하나를 충족하면 다음 자동 라운드를 시작하지 않는다.

- 설정한 최대 라운드 도달
- 모든 Critical 및 Major 차단 쟁점이 해결됨
- 새로운 중요 쟁점과 실질적인 결과 변경이 없음
- 사용자 결정이 없으면 다음 단계가 무의미함
- 인증, 구독 한도, 시간 제한 또는 복구 불가능한 출력 오류 발생
- 사용자의 일시정지 또는 취소

설정한 라운드가 2이고 아직 3라운드에 도달하지 않았다면, 질문 카드에서 `한 라운드 더 토론`을 선택지로 제공할 수 있다.

### 12.3 수렴 판정

다음 조건을 모두 충족하면 수렴한 것으로 본다.

- `blocking=true`인 모든 Critical 및 Major 쟁점이 `RESOLVED` 또는 근거를 갖춘 `SUPERSEDED` 상태다.
- `AWAITING_EVIDENCE`, `AWAITING_USER`, `OPEN` 상태의 차단 쟁점이 없다.
- 필수 문서 섹션 또는 필수 분석 항목이 모두 존재한다.
- 수용 항목의 실제 반영 위치가 기록되어 있다.
- 거부 항목에 구체적인 이유가 있다.
- 양쪽 결과의 남은 차이가 의도된 차이인지 설명되어 있다.

Minor 쟁점만 남으면 경고와 함께 최종 산출물에 기록하고 완료할 수 있다.

## 13. 구조화된 쟁점 원장

자유 형식 Markdown 토론문과 별개로 검증 가능한 `issues.json`을 유지한다. 상태 변경은 모델의 일반 문장을 임의로 추론하지 않고 JSON 스키마 검증을 통과한 구조화 결과만 사용한다.

`workflow-v2`의 각 쟁점은 최소한 다음 필드를 가진다.

```json
{
  "issueId": "D-004",
  "round": 2,
  "raisedBy": "claude",
  "targetDocumentId": "A",
  "category": "scope",
  "severity": "major",
  "claim": "오프라인 동작 범위가 정의되지 않았다.",
  "evidence": [
    {
      "sourceDocumentId": "B",
      "proposedByProvider": "claude",
      "path": "PRD.md",
      "location": "7.2 기능 요구사항",
      "excerptHash": "sha256:..."
    }
  ],
  "proposal": "읽기 전용 또는 작성·동기화 범위를 명시한다.",
  "responses": {
    "codex": "초기 릴리스는 읽기 전용만 지원한다.",
    "claude": "작성과 임시 저장까지 포함해야 한다."
  },
  "editorialDecisions": [
    {
      "targetDocumentId": "A",
      "performedBy": "codex",
      "disposition": "PARTIALLY_ACCEPTED",
      "rationale": "동기화 충돌 해결은 초기 범위를 초과한다."
    }
  ],
  "reviewerVerdicts": [
    {
      "targetDocumentId": "A",
      "reviewer": "claude",
      "verdict": "DISAGREES",
      "rationale": "핵심 사용 흐름이 오프라인 작성을 요구한다."
    }
  ],
  "adoptions": [
    {
      "targetDocumentId": "A",
      "sourceDocumentId": "B",
      "proposedByProvider": "claude",
      "performedBy": "codex",
      "disposition": "PARTIALLY_ACCEPTED",
      "locations": ["PRD.md#비기능-요구사항"],
      "round": 2
    }
  ],
  "requiresUser": false,
  "blockingProposals": {
    "codex": false,
    "claude": true
  },
  "blocking": true,
  "resolutionStatus": "RESOLVED"
}
```

쟁점 원장 규칙은 다음과 같다.

- 쟁점 ID는 실행이 끝날 때까지 변경하지 않는다.
- 의미상 같은 쟁점은 삭제하지 않고 대표 쟁점에 연결한다.
- 상태 변경 이력을 덮어쓰지 않고 이벤트로 추가한다.
- workflow-v2의 새 `issueKey`는 공급자·라운드·단계·대상을 포함한 안정적인 형식으로 실행 전체에서 고유해야 한다. `issueResponses`, `adoptions`, `openQuestions`는 같은 결과 또는 확정된 선행 산출물에 존재하는 키만 참조하고, 참조 대상 문서가 원래 쟁점의 A/B 대상과 다르면 저장 전에 실패 폐쇄한다.
- `openQuestions.options`에는 사용자가 실제로 선택할 수 있고 서로 다른 대안 두 개 또는 세 개만 허용한다. `recommendedOption`은 그중 하나의 문구 또는 대응하는 A/B/C 코드여야 하며, 필드 설명·자리 표시·권장안 유무 같은 메타 문구가 선택지에 들어오면 저장 전에 실패 폐쇄하고 형식 복구 대상으로 처리한다. `safeDefault`는 추가 선택지가 아니라 사용자가 답하기 전까지 지킬 안전 동작을 설명한다.
- workflow-v2의 내부 issues/evidence/adoptions는 단계별 대상·출처 허용 행렬을 따르며 각 항목의 `targetDocumentId`와 `sourceDocumentId`는 단계 결과 상위의 `targetDocumentId`와 `sourceDocumentIds` 범위를 벗어날 수 없다.
- `editorialDecisions`는 대상 문서별 편집 판단이며 `performedBy`는 해당 단계의 작업자를 나타낼 뿐 소유권을 뜻하지 않는다.
- `reviewerVerdicts`는 편집 판단을 평가할 뿐 채택 여부를 대신 결정하지 않는다.
- 한 쟁점이 A/B에 서로 다르게 반영되면 대상별 `editorialDecisions`, `reviewerVerdicts`와 `adoptions`를 각각 보존한다.
- `sourceDocumentId`와 `proposedByProvider`를 분리하여 문서 출처와 제안 작업자를 혼동하지 않는다.
- `REJECTED` 판단에는 구체적인 이유 또는 근거가 있어야 한다.
- `ACCEPTED`와 `PARTIALLY_ACCEPTED` 판단에는 대상 문서, 실제 반영 위치와 라운드가 있어야 한다.
- workflow-v2 원장은 `reviewerVerdicts`, `editorialDecisions`, `adoptions`의 출처 단계와 라운드, 대상, 판단, 이유와 위치 타입을 저장 전에 검증하며 레거시 `ownerDecisions`를 섞지 않는다.
- `workflow-v1`의 `ownerDecisions`는 레거시 스키마로 그대로 읽고 저장 원본을 `editorialDecisions`로 재작성하지 않는다.
- 모델은 `blockingProposals`에 차단 여부와 이유를 제안할 수 있지만 최종 `blocking` 값은 오케스트레이터만 계산한다.
- 모든 Critical 쟁점은 오케스트레이터가 항상 `blocking=true`로 강제한다. 모델이 `false`를 제안하거나 잘못 출력해도 완화하지 않는다.
- Major는 필수 산출물 누락, 핵심 요구사항 위반, 안전·정합성 실패, 사용자 결정 또는 추가 근거 없이는 진행할 수 없는 경우에 `blocking=true`로 계산한다. 그 외 Major는 비차단으로 둘 수 있으나 최종 결과 상단에 남긴다.
- `blocking=true`인 쟁점은 `RESOLVED`가 되기 전까지 `COMPLETED`를 허용하지 않는다.
- 해결되지 않은 Critical 또는 Major `AWAITING_EVIDENCE` 쟁점은 근거를 요청해 실행을 대기시키거나 `COMPLETED_PARTIAL`로만 종료한다.
- 근거 없이 `동의`, `개선`, `해결`이라고만 쓴 응답은 완료로 인정하지 않는다.
- 사실, 가정, 선호와 권고를 구분한다.
- 입력에서 확인할 수 없는 주장은 `검증되지 않은 가정`으로 표시한다.

## 14. 사용자 결정과 설명

### 14.1 사용자 질문 게이트

다음 쟁점만 사용자 질문으로 승격한다.

- 제품 범위, 비용, 일정 또는 위험 선호에 따라 답이 달라지는 쟁점
- 양쪽 모두 합리적인 대안을 제시하여 객관적 우열을 정하기 어려운 쟁점
- 최대 라운드 후에도 남아 있는 Critical 또는 Major 쟁점
- 요구사항이 모호하여 임의 결정 시 결과가 크게 달라지는 쟁점
- 입력만으로 근거를 확보할 수 없고 사용자의 의도가 필요한 쟁점

중대한 입력 누락 때문에 추가 토론이 낭비되는 경우에는 최대 라운드 전이라도 체크포인트에서 일찍 질문할 수 있다. 유사한 질문은 합치고 우선순위 순으로 한 번에 최대 3개만 보여준다. 차단 질문이 더 있으면 현재 배치 처리 후 다음 배치를 보여주며, 모든 차단 질문이 처리되기 전에는 최종화하지 않는다.

현재 단계의 모든 질문에 답하면 그 답변을 양쪽 최종 문서·검증 단계에 반영해 다시 검토한다. 검토 결과 새 사용자 결정이 필요한 경우에만 다음 사용자 확인 단계를 열며, 최초 단계를 포함해 최대 3회까지만 허용한다. 질문이 더 필요하지 않으면 3회를 채우지 않고 즉시 완료한다. 세 번째 단계의 답변을 검토한 뒤에도 새 차단 질문이 생기면 네 번째 단계를 열지 않고 `QUESTION_LIMIT_REACHED`로 종료하며 새 질문, 미해결 쟁점과 결과 문서를 보존한다. 이 상태를 `COMPLETED` 또는 `COMPLETED_PARTIAL`로 바꾸어 표시하지 않는다.

### 14.2 질문 카드

각 질문 카드는 다음 내용을 포함한다.

- 쟁점 ID와 제목
- 지금 결정해야 하는 이유
- 비전문가도 이해할 수 있는 쉬운 설명
- Codex 의견과 근거
- Claude 의견과 근거
- 질문 화면은 `현재 상태 → 핵심 쟁점 → AI 검토와 문서 처리 → 사용자에게 요청하는 것 → 선택 결과` 순서로 설명하고, 승인 요청·방향 선택·자료 요청 중 사용자가 해야 할 행동과 그 목적을 먼저 밝힌다.
- 질문·결정 화면의 문서 계보는 `문서 A/문서 B/최종 문서`, 사용자 선택은 `1안/2안/3안`, AI 작업자는 `Codex/Claude`로 표기 체계를 분리한다. 화면에서 선택지 A/B 표기를 사용하지 않으며 내부 결정 코드 A/B와 기존 CLI 입력 호환성만 유지한다.
- AI별 기록에는 누가 문제를 제기했고 무엇에 동의·반대했는지, 문서에 잠정 반영된 내용이 있는지와 사용자 승인 전인지 표시한다. `제안 내용`, `현재 요구`, `앞 단계 판단`처럼 앞 문맥 없이는 뜻을 알 수 없는 표현만으로 선택지나 의견을 구성하지 않는다.
- 질문에 공급자별 설명이 없으면 모호한 상세 보기 안내를 반복하지 않고, 원장에 저장된 최신 검토 판정을 쉬운 문장으로 보여주거나 구체적인 기록이 없다고 밝힌다.
- 한 질문의 답을 기록하면 미답변 질문 수를 알리고 다음 질문 배치를 이어서 표시한다. 사용자가 중간에 나가도 실행 상태와 별개로 `pending.json`의 미답변 질문 수를 읽어 작업 메뉴에서 다시 진입할 수 있어야 하며, 미답변 질문이 남아 있는 동안 `작업 계속하기`는 이유와 함께 비활성화한다.
- 질문 화면과 작업 화면에는 현재 질문 검토 관문을 `1/3`, `2/3`, `3/3`으로 표시한다. `3/3`에서는 현재 질문을 모두 답한 뒤 새 질문이 생겨도 자동 재질문하지 않는다는 경고를 함께 표시한다.
- 기본 질문 카드는 작은 높이에서도 섹션 제목과 2칸 들여쓴 본문을 서로 다른 행으로 유지하고, 가용 높이를 핵심 쟁점, 제안 방향과 사용자 요청에 우선 배분해 여러 줄로 표시한다. 기본 카드에서 줄어든 내용은 같은 질문의 `[M] 자세히 보기·추가 검토 → 질문 내용 전체 보기`에서 저장·검증된 구조화 필드를 생략 없이 공백 우선 줄바꿈하여 터미널 스크롤로 읽고 결정 화면으로 돌아올 수 있어야 한다. `[M]`에는 추가 토론·AI 상세 설명·양쪽 의견 비교만 함께 두며 자유 입력이나 공통 전제를 중복 제공하지 않는다. 이 경로도 원시 stdout/stderr, 생성 중 텍스트, 전체 문서, 프롬프트와 모델 응답 원문을 노출하지 않는다.
- 이전 답변 변경 목록에는 대상 문서, 질문 제목과 현재 답변을 함께 표시한다. 항목을 선택하면 원래 질문, 핵심 쟁점과 현재 답변을 독립 섹션과 들여쓴 전체 본문으로 새 선택지보다 먼저 표시하고 현재 답변에 초기 커서를 둔다. 신규 답변 기록은 선택지와 함께 질문 제목·문장을 보존한다. 이 필드가 없는 기존 실행은 저장된 쟁점과 선택지로 질문을 복원했다는 사실을 명시하며 정확한 원문인 것처럼 표시하지 않는다. 추가 자료 요청 목록은 짧은 식별 정보만 표시하고, 항목을 선택한 뒤 핵심 쟁점과 필요한 자료의 전체 내용을 경로 선택 전에 보여준다.
- 객관식 선택지와 같은 첫 화면에 `선택지에 없는 내 의견 직접 입력`을 제공하고, 입력 전에 `이 질문의 주관식 답변`과 `여러 질문에 공통 전제` 중 적용 방식을 고르게 한다. 주관식 답변은 현재 질문을 완료하고 공통 전제는 현재 질문을 완료하지 않는다는 차이를 메뉴 설명과 미리보기에서 반복해 알린다.
- 선택지별 장점, 단점, 예상 비용과 위험
- 되돌리기 난이도
- 공동 권고안 또는 권고가 갈리는 이유
- 권고 신뢰도
- 모를 때 선택할 안전하고 되돌리기 쉬운 기본값
- 프로토타입이나 실험으로 미룰 수 있는지
- 결정하지 않을 경우의 영향

### 14.3 사용자 동작

사용자는 다음 동작을 할 수 있다.

- 특정 선택지 선택
- 공동 권고안대로 진행
- Codex 관점 상세 설명 요청
- Claude 관점 상세 설명 요청
- 양쪽 설명을 나란히 비교
- 초급, 일반 또는 전문가 수준의 설명 요청
- 구체적인 사례 요청
- 개발 비용과 난이도 비교 요청
- 검증 실험 설계 요청
- 한 라운드 추가 요청(최대 3라운드 이내)
- 결정 보류
- 선택지 대신 자유 입력을 이 질문의 주관식 답변으로 확정
- 여러 질문에 함께 적용할 자유 입력 공통 전제 제공

### 14.4 설명 및 결정 규칙

- 설명 요청 중 실행 상태는 `AWAITING_USER`를 유지한다.
- 설명은 문서나 쟁점 상태를 임의로 변경하지 않는다.
- 설명 요청은 라운드 수에 포함하지 않는다.
- 사용자는 같은 쟁점에 여러 번 설명을 요청할 수 있다.
- 양쪽 관점 설명은 같은 근거 스냅샷을 사용한다.
- 설명에서 새로 제시된 사실과 기존 판단을 명확히 구분한다.
- 사용자 답변 원문, 해석된 결정, 영향을 받는 쟁점과 산출물 위치를 기록한다.
- 자유 입력은 즉시 적용하지 않고 `이 질문의 주관식 답변` 또는 `여러 질문에 공통 전제`로 해석한 미리보기를 보여준 뒤 정확한 `APPLY` 확인을 받아 적용한다.
- 주관식 답변은 기존 `ANSWER` 결정으로 기록해 현재 질문을 답변 완료로 처리한다. 공통 전제는 기존 `CONSTRAINT` 결정으로 기록해 현재 질문을 미답변으로 유지하며, 현재·이후의 객관식 및 주관식 답변과 함께 두 AI의 마지막 문서 생성·검증 단계에 적용한다.
- 공통 전제와 개별 답변이 양립할 수 없으면 AI는 어느 한쪽을 조용히 버리지 않고 새 차단 쟁점을 제기한다.
- 사용자는 최종 확정 전까지 결정을 변경할 수 있고 변경 이력을 보존한다.
- 결정이 변경되면 그 결정을 소비한 단계와 산출물을 `STALE`로 표시하고 최초 영향 단계 이후만 다시 실행한다. 이전 산출물은 감사 이력으로 보존한다.
- 사용자가 답하면 해당 결정은 이후 모든 AI 호출에 공통 제약으로 주입한다.
- 사용자 결정은 두 AI에 구속력이 있다. 반영이 안전하지 않거나 논리적으로 불가능하면 새 차단 쟁점을 만들고 사용자의 결정을 조용히 무시하지 않는다.
- 모든 차단 질문이 처리되면 `결정 반영 → 영향받은 문서 재생성 → 결정 ID별 반영 검증`의 최종화 단계를 한 번 수행한다. 이 단계는 토론 라운드에 포함하지 않는다.
- 사용자가 `권고안대로 진행`을 선택하면 되돌리기 쉬운 대안을 우선한다.
- 실험으로 결정하는 선택은 v1에서 실험 계획만 기록하며 코드를 실행하지 않는다.
- Minor 쟁점 보류는 경고와 함께 `COMPLETED`를 허용한다. Critical 또는 Major 쟁점 보류는 사용자의 명시적 확인 후 `COMPLETED_PARTIAL`만 허용하고 최종 결과 상단에 표시한다.
- v1은 모델 응답 생성 도중이 아니라 각 호출 또는 라운드가 끝나는 체크포인트에서만 일시정지한다.
- 사용자는 `--pause-after-round`를 지정하거나 실행 중 `pause`를 요청할 수 있다. 요청은 현재 모델 호출을 끊지 않고 다음 호출 전에 반영한다.
- 일시정지 체크포인트에서는 원장에 등록된 어떤 쟁점이든 설명을 요청할 수 있다. 시스템이 먼저 `ASK_USER`로 승격한 쟁점에 한정하지 않는다.

## 15. CLI 사용자 경험

DuoForge는 **메뉴 우선, 명령어 병행** 구조를 사용한다. 일반 사용자의 기본 진입점은 인수 없는 `duoforge`이며, 자동화·반복 실행·진단이 필요한 고급 사용자를 위해 같은 도메인 기능을 호출하는 명시적 하위 명령을 제공한다. 메뉴와 고급 CLI가 실행 계획, 검증, 상태 저장과 오류 처리 로직을 각각 구현해서는 안 된다.

### 15.1 기본 진입점과 홈 메뉴

대화형 터미널에서 인수 없이 `duoforge`를 실행하면 커서 이동·`Enter` 중심의 홈 메뉴를 연다.

```text
DuoForge

> [1] 새 작업 시작
[2] 진행 중인 작업 이어하기 (1)
[3] 완료된 결과 보기
[4] 포기한 작업 관리 (0)
[5] 환경 진단, 로그인 및 설정
[Q] 종료

↑/↓ 이동 · Home/End · Enter 선택 · Esc/Q 종료
```

- 공통 메뉴 선택기는 `↑/↓` 순환 이동, `Home/End`, `Enter` 확정과 하위 화면의 `Esc` 이전을 기본으로 제공한다. 숫자·영문 단축키는 해당 항목을 즉시 선택한다. 홈에서 `Esc`, `Q`, `Ctrl+C`는 모두 종료이며 `B`는 홈 조작으로 사용하지 않는다. 색상을 지원하는 커서 메뉴에서는 현재 커서가 놓인 항목 본문을 청록색으로 강조하고, 그 아래 추가 설명과 비활성 이유 본문은 어두운 회색으로 분리한다.
- 비활성 항목도 목록에서 위치를 유지하고, 커서가 놓이면 사용할 수 없는 이유를 함께 표시한다.
- 모델과 분석 깊이 화면의 권장 항목은 처음 강조할 수 있지만, 강조만으로 선택된 것으로 보지 않고 반드시 `Enter` 또는 단축키 확정을 요구한다.
- VT를 지원하면 ANSI 커서 렌더링을 사용하고, VT가 없더라도 Windows 콘솔 커서 API를 사용할 수 있으면 같은 방향키 메뉴를 유지한다. 두 커서 렌더링 방식과 키 읽기를 사용할 수 없거나 렌더링이 실패할 때만 ANSI 없는 줄 입력 메뉴로 한 번 폴백한다. 비대화형·리디렉션 환경에서는 입력을 기다리지 않는다.
- 모든 대화형 입력은 문자열이나 빈 값 대신 `submit`, `back`, `cancel`, `interrupt`, `invalid`, `unavailable`을 구분하고 실제 제출값, 입력 출처와 `parent`, `work-menu`, `home`, `shell` 중 복귀 위치를 함께 전달한다.
- 하위 선택·확인 화면의 물리 `Esc`와 표시형·줄 입력 폴백의 `B`는 바로 위 부모 화면으로만 돌아가는 `back`이다. `Q`는 현재 다단계 흐름을 변경 없이 끝내고 가장 가까운 작업 메뉴·홈·CLI 셸로 돌아가는 `cancel`이다. `Ctrl+C`는 긴급 `interrupt`로 분류하고 콘솔 상태를 복원한 뒤 최상위 경계로 전파한다.
- 잘못된 입력은 취소로 바꾸지 않고 이유를 설명한 뒤 같은 화면에 남는다. 외부 동작이 시작되기 전 선택·확인 경계의 `back`, `cancel`, `interrupt`, `invalid`, `unavailable`은 공급자 호출, 로그인, 재개, run 생성, 파일·답변·제약·자료 기록 또는 단계 reset을 만들지 않는다. AI 실행 중 `interrupt`는 기존 체크포인트 보존 중단 계약을 따른다.
- 자유 텍스트·경로·모델명 입력의 `B`와 `Q`는 탐색키가 아니라 제출 가능한 데이터로 보존한다. 지원 터미널은 PowerShell 7 독립 ConsoleHost와 Windows Terminal로 한정하며 편집기 통합 터미널은 지원 범위에 포함하지 않는다. 일반 자유 입력은 두 지원 터미널에서 검증한 줄 입력을 유지하고 raw 입력 편집기를 도입하지 않으며, 입력 전 명시적인 이전 메뉴를 제공한다.
- `LIVE`, `PARTIAL`, `ROUND`, `APPLY`, `DEFER`, `ABANDON`, `RESTORE`, `DELETE`는 대소문자를 구분한 정확한 대문자 토큰과 `Enter`에서만 확정한다. 앞뒤 공백을 자동 제거하지 않으며 앞뒤·중간 공백, 빈 값, 소문자와 오타는 `invalid`로 처리해 같은 확인 화면에서 다시 입력받는다.
- Windows 파일·폴더 선택기의 닫기·취소는 `back`으로 분류하고 선택기 실행 실패와 구분한다.
- 첫 실행 또는 진단 결과가 만료된 경우 홈 메뉴 진입 시 `doctor`를 자동 실행한다. 로그인이 없거나 만료되었으면 새 작업 메뉴보다 안내형 로그인 동작을 우선 보여주고, 다른 문제에는 해결 방법과 다시 검사 동작을 제공한다.
- 진행 중인 실행이 하나면 사람이 읽을 수 있는 작업 이름, 모드, 현재 상태와 다음 동작을 바로 표시한다.
- 진행 중인 실행이 여러 개면 최근 갱신 순으로 선택하게 하며 내부 `runId`는 상세 정보에서만 노출한다.
- `이 작업 포기`는 정확한 `ABANDON` 확인 뒤 실행을 `CANCELLED`로 종료하고 재개를 막되 문서 사본과 감사 기록을 보존한다. 포기한 실행은 진행 중·완료 목록과 분리한 `포기한 작업 관리`에 표시한다.
- `이 작업 복원`은 `CANCELLED` 실행에만 제공한다. 정확한 `RESTORE` 확인 뒤 이전 상태가 아니라 항상 `PAUSED_USER`로 바꾸고 `restoredAt`과 `RUN_RESTORED`를 남기며, 복원 자체는 AI 작업이나 재개를 시작하지 않는다.
- `이 작업 영구 삭제`는 `CANCELLED` 실행에만 제공한다. 정확한 `DELETE` 확인 전에는 어떤 파일도 변경하지 않으며, 확인 뒤 실행 결과 루트의 직계 작업 폴더 전체를 삭제한다. 원본 입력 문서는 삭제하지 않는다.
- 메뉴가 열릴 수 없는 비대화형 표준입력, 리디렉션, CI 또는 원격 무인 환경에서는 입력을 기다리지 않는다. 도움말과 필요한 명시적 명령을 출력하고 비정상 대기 없이 종료한다.
- 모든 사람용 터미널 출력은 `화면 제목 → 상태 태그 → divider → 큰 섹션 → 필드·목록 → 알림·다음 행동`의 공통 문법을 사용한다. 큰 섹션은 `── 제목` 표식을 남기고 본문은 2칸, 하위 본문은 4칸 들여쓴다. 긴 필드·목록·명령은 현재 터미널의 `WindowWidth - 1` 안에서 공백 우선으로 줄바꿈하며 이어진 줄은 값 또는 본문 시작 열에 맞춘다. 정보·상태·경고 블록 뒤에 별도의 선택 메뉴가 이어지면 메뉴 제목 바로 앞에 빈 행 하나를 두되 중복하지 않는다. 단, 20~23행 질문 카드는 바로 아래 선택 메뉴에 요청 종류가 반복될 때 한 줄 식별자만 남기고 상태 태그와 divider를 생략하며, 전환 여백을 위해 메뉴 내부 설명을 한 행으로 줄여 핵심 쟁점·AI 처리·사용자 결정의 제목과 본문 및 전체 높이를 보존할 수 있다.
- 사람용 화면은 내부 구현 용어를 행동과 결과 중심의 일상어로 바꾼다. `provider`, `budget`, `snapshot`, `batch`, `stepKey`, `LIVE` 같은 내부 개념은 각각 `Codex/Claude`, `AI 요청 횟수`, `작업 시작 때 보관한 문서`, `읽을 수 있는 범위`, `회차·AI·작업명`, `확인어 LIVE`로 표시한다. 저장 JSON·이벤트·진단 코드의 내부 필드명과 값은 바꾸지 않는다.
- 앞으로 가능한 요청 수는 `예정 요청`, `실패 시 추가 요청`, `최대 요청`으로 나누어 표시한다. 답변 변경 등으로 다시 만드는 작업은 오류 재시도로 부르지 않는다. 마지막 완료 지점과 답변·제약·자료 반영 결과에는 `r02-claude-review-response` 같은 내부 단계 ID를 노출하지 않는다.
- 큰 섹션 사이는 기본 한 줄을 비우되 높이 20~23의 compact 화면에서는 공백만 줄이고 섹션 표식은 유지한다. 상세·스크롤 화면은 정제된 문단 경계와 섹션 공백을 보존하며 섹션 제목만 프레임 마지막 줄에 남기지 않는다.
- 색상은 의미를 보조할 뿐 유일한 구분 수단으로 사용하지 않는다. 무색 또는 Unicode를 사용할 수 없는 환경에서도 `--`, `OK`, `X`, `!`, `i` 같은 표식으로 같은 정보 순서, 상태와 다음 행동을 이해할 수 있어야 한다.

### 15.2 최초 로그인과 재인증

사용자는 DuoForge를 실행하기 전에 Codex와 Claude를 미리 인증할 필요가 없다. 다만 모든 실제 모델 호출 전에는 두 공급자의 구독 로그인이 모두 유효해야 한다. 첫 실행, 로그아웃 또는 인증 만료가 감지되면 다음 안내 화면을 연다.

```text
DuoForge 최초 설정

✓ Codex CLI 설치됨
✓ Claude Code CLI 설치됨
✗ Codex 로그인이 필요합니다.
✗ Claude 로그인이 필요합니다.

[1] Codex 로그인 시작
[2] Claude 로그인 시작
[3] 다시 검사
[Q] 종료
```

#### 로그인 실행

- `Codex 로그인 시작`은 전경 대화형 프로세스로 `codex login`을 실행한다. 사용자는 공급자가 연 브라우저에서 ChatGPT 구독 계정 인증을 직접 완료한다.
- `Claude 로그인 시작`은 전경 대화형 프로세스로 `claude auth login`을 실행한다. 사용자는 공급자가 연 브라우저에서 Claude Pro, Max, Team 또는 Enterprise 구독 계정 인증을 직접 완료한다. v1은 API 사용량 청구용 Console 로그인을 선택하는 `--console`을 사용하거나 권장하지 않는다.
- 두 로그인은 동시에 실행하지 않고 한 번에 하나씩 진행한다. 로그인 프로세스가 종료되면 현재 화면으로 돌아와 해당 공급자만 즉시 다시 검사한다.
- 브라우저를 자동으로 열 수 없으면 공급자 CLI가 제공하는 URL 복사, 기기 코드 또는 코드 붙여넣기 흐름을 그대로 보여준다. DuoForge가 인증 URL이나 코드를 임의로 재구성하지 않는다.
- 사용자가 로그인 화면을 취소하거나 브라우저를 닫으면 모델 호출 없이 최초 설정 화면에 남고 다시 시도, 수동 명령 보기 또는 종료를 선택하게 한다.

#### 상태 확인과 완료

- Codex는 `codex login status`, Claude는 `claude auth status`의 종료 코드와 지원 버전의 구조화 출력을 이용해 로그인 여부와 활성 인증 유형을 확인한다.
- `doctor`는 단순히 자격증명이 존재하는지만 보지 않고 ChatGPT·Claude 구독 인증이 실제 활성 방식인지 확인한다. 정확한 출력 필드는 공급자 버전별 어댑터 기능 검사로 판별한다.
- 두 구독 인증이 확인되면 다음처럼 완료 상태를 보여주고 홈 메뉴 또는 시작하려던 작업으로 돌아간다.

```text
DuoForge 최초 설정 완료

✓ Codex: ChatGPT 구독 로그인
✓ Claude: Claude.ai 구독 로그인
✓ API 자격증명 우선 조건 없음

[Enter] 계속
```

- 공급자 CLI가 저장한 인증은 이후 실행에서 재사용한다. DuoForge는 마지막 확인 시각, 공급자, 공개 가능한 인증 유형과 결과 코드만 저장하며 공급자 인증 파일을 복사하지 않는다.
- DuoForge는 이메일, 비밀번호, 브라우저 인증 코드, 액세스 토큰, API 키 또는 공급자 인증 파일 내용을 입력받거나 로그·상태·매니페스트에 저장하지 않는다.
- 인증이 만료되면 같은 안내형 흐름을 `재로그인`으로 표시하고, 성공 후 중단된 실행의 사전 검사 또는 마지막 체크포인트로 돌아간다.
- API 키 또는 API 인증 우선 조건이 감지되면 값을 표시하거나 환경 변수를 자동 삭제하지 않는다. 변수 이름, API 과금 가능성, 구독 인증으로 복구하는 공식 명령과 `다시 검사`만 제공한다.
- 활성 인증을 바꾸기 위해 공급자에서 로그아웃해야 하는 경우에는 기존 CLI 작업에도 영향을 줄 수 있음을 알리고 사용자의 명시적 선택 없이 자동 로그아웃하지 않는다.
- 비대화형 표준입력, 리디렉션, CI와 원격 무인 실행에서는 로그인 프로세스나 브라우저를 시작하지 않는다. 두 구독 인증이 미리 완료되지 않았으면 공급자별 로그인 명령과 오류 코드를 출력하고 종료한다.

### 15.3 새 작업 마법사

`새 작업 시작`은 내부 모드명보다 사용 목적을 먼저 보여준다.

```text
무엇을 하시겠습니까?

[1] 요구사항으로 공동 문서 만들기
[2] 두 문서를 비교해 하나의 합의안 만들기
[3] 두 문서를 각각 개선하기
[4] 두 프로젝트 비교하기 · 준비 중
[B] 이전으로
```

선택한 목적은 각각 `shared-document`, `document-merge`, `dual-document`, `dual-project-audit`에 매핑한다. 일반 흐름에서는 내부 모드명을 입력하게 하지 않는다. 모드 4를 선택하면 현재 격리 실패와 필요한 안전 게이트를 설명하고 `DF-PREFLIGHT-3A-ISOLATION`으로 모델 호출 전에 종료한다.

- 공동 합의 문서는 주요 Markdown 파일 또는 짧은 설명 파일 하나를 선택한다.
- 모드 2·3은 문서 A와 문서 B를 순서대로 선택하고 선택 결과와 각 부모 폴더에서 자동 포함될 보조 Markdown을 나란히 확인한다. 두 주요 문서가 같은 폴더 또는 서로 중첩된 폴더에 있으면 진행하지 않고 별도 폴더 구성을 안내한다. A/B의 추가 보조 문서 폴더는 고급 설정에서 선택할 수 있다.
- 프로젝트 읽기 전용 비교는 현재 비활성이다. 향후 게이트 충족 시 프로젝트 A, 프로젝트 B와 공통 요구사항 문서를 순서대로 선택한다.
- 문서 유형은 파일명과 내용으로 추정하여 제안하되 사용자가 확인하거나 바꿀 수 있게 한다.
- Codex와 Claude 각각에 대해 모델과 추론 정도를 반드시 선택한다. Codex는 실행 시 CLI의 계정별 모델 카탈로그와 모델별 기본·지원 추론 정도를 다시 조회하고, Claude는 CLI가 현재 광고하는 버전 비고정 별칭·effort와 계정 기본(`default`)을 다시 읽는다. 현재 목록에 존재할 때만 `gpt-5.6-sol + high`, `opus + high`를 권장하고, 모델이나 단계가 사라지면 CLI 기본 모델·기본 추론 정도로 이동한다. 추천 목록과 모델명 직접 입력을 제공하되 사용자의 선택 없이 기본값으로 진행하지 않는다.
- 선택한 네 값은 실행 전 확인과 매니페스트에 기록하고 모든 해당 공급자 호출에 동일하게 전달한다. 선택값이 없는 이전 실행은 라이브 재개하지 않는다.
- 라운드는 기본 2, 결과 루트는 기본적으로 `D:\Coding\APP-windows\DuoForge\results`로 자동 설정한다. 최대 라운드, 일시정지, 추가 보조 문서 폴더와 사용자 지정 결과 루트는 `고급 설정`에서만 노출한다.
- 마법사 도중 뒤로 가거나 취소하면 모델을 호출하거나 실행 디렉터리를 확정 생성하지 않는다.
- AI 작업 직전에는 보관된 문서의 전송 범위, 사용할 AI 설정과 `예정 요청`, `실패 시 추가 요청`, `최대 요청`을 하나의 최종 확인 화면에서 보여준다. 확인 문자열 `LIVE`는 기능명이 아니라 문서 전송과 AI 작업 시작에 동의하는 확인어라고 설명한다.

### 15.4 파일·폴더 선택

대화형 메뉴의 입력 선택은 다음 세 방식을 함께 제공한다.

```text
입력 문서를 선택해 주세요.

[1] Windows 파일 선택창 열기
[2] 경로 붙여넣기 또는 파일 끌어놓기
[3] 최근 사용한 파일
[B] 이전으로
```

#### Windows 선택창

- 파일 입력에는 표준 Windows 파일 선택창을, 프로젝트·보조 문서·출력 위치에는 표준 Windows 폴더 선택창을 연다.
- Markdown 입력 선택창은 기본적으로 `.md` 파일을 필터링한다.
- 선택창은 대화형 Windows 데스크톱 세션에서만 사용하며, 선택창을 열 수 없으면 오류로 막지 않고 경로 입력 방식으로 전환한다.
- 선택 취소는 작업 전체 취소가 아니라 현재 선택 단계로 돌아오는 동작이다.

#### 경로 붙여넣기와 드래그 앤 드롭

- 사용자는 Windows Explorer의 파일이나 폴더를 터미널에 끌어놓거나 경로를 붙여넣을 수 있다.
- 입력값의 바깥쪽 따옴표와 드래그 앤 드롭 시 생긴 공백을 정규화하고, 상대 경로는 현재 작업 폴더를 기준으로 절대 경로로 변환한다.
- 경로 문자열을 셸 명령으로 평가하거나 `Invoke-Expression`으로 확장하지 않는다.
- 파일 입력 단계에 폴더가 들어오거나 폴더 입력 단계에 파일이 들어오면 원인을 설명하고 같은 단계에서 다시 선택하게 한다.

#### 최근 사용 경로

- 최근 사용 파일과 폴더는 경로, 역할, 마지막 사용 시각만 로컬 설정에 저장하며 파일 내용은 저장하지 않는다.
- 존재하지 않거나 현재 접근할 수 없는 최근 경로는 선택 시 이유를 알리고 다시 선택하게 한다.
- 사용자는 최근 경로 기록을 개별 삭제하거나 모두 지울 수 있다.
- 최근 경로는 편의 기능일 뿐 실행 매니페스트나 감사 기록의 근거를 대신하지 않는다.

#### 선택 직후 검증

각 선택 직후 다음 정보를 보여주고 계속, 다시 선택 또는 이전 단계로 이동할 수 있게 한다.

```text
선택한 문서

D:\Projects\MyApp\brief.md

유형: Markdown
크기: 18.4 KiB
상태: 정상

[Enter] 계속
[C] 다시 선택
[B] 이전으로
```

- 절대 경로, 입력 역할, 유형, 크기 또는 예상 파일 수, 읽기 가능 여부를 표시한다.
- 한글, 공백, 긴 Windows 경로와 UNC 경로의 지원 여부를 즉시 검증한다.
- 두 문서 또는 두 프로젝트의 동일 경로, 중첩 경로, 링크 탈출과 출력 위치 중첩은 실행 전 차단한다.
- 모드 2·3에서는 두 주요 문서의 부모 폴더가 같거나 중첩되어도 차단한다. 다음과 같이 현재 선택, 차단 이유와 어느 문서를 다시 선택할지 보여준다.

```text
이 문서 조합은 사용할 수 없습니다.

문서 A: D:\Documents\Debate\A\main.md
문서 B: D:\Documents\Debate\B\main.md

두 문서가 같은 폴더에 있습니다.
DuoForge는 각 문서 폴더의 다른 Markdown을 해당 측 보조 문맥으로 자동 포함하므로
두 주요 문서는 서로 분리되고 중첩되지 않은 폴더에 있어야 합니다.

[1] 문서 A 다시 선택
[2] 문서 B 다시 선택
[B] 이전으로
```

- 권장 구조는 `...\A\main.md`와 `...\B\main.md`이며, 각 폴더의 보조 Markdown 목록을 선택 확인 화면에 함께 표시한다.
- 기본 결과 루트는 입력 문서의 부모 폴더·프로젝트 밖에 두며, 사용자가 다른 결과 위치를 선택해도 동일한 경계 검사를 적용한다.

### 15.5 실행 현황, 결정과 결과 메뉴

홈 메뉴와 `이어하기` 화면은 상태 이름만 보여주지 않고 현재 사용자가 할 수 있는 다음 동작을 우선 표시한다.

대화형 라이브 실행은 실제 단계 의존성을 장벽 레일로 표현하는 풀스크린 `LIVE` 진행판을 연다. 진행판은 현재 공급자·단계·대상 문서·경과 시간, 완료·실행·재시도·대기 상태와 검증·커밋된 최근 결과 최대 3건을 표시한다. 실제 가용 행이 충분하면 실행 흐름을 전부 표시하고, 부족하면 현재 장벽 주변을 유지하면서 `앞 N단계 생략`과 `뒤 N단계 생략`으로 누락 방향과 정확한 개수를 알린다. 현재 작업은 기존 프로세스 대기 루프의 경과 시간에서 500ms 단위로 계산한 `PROVIDER_TICK`만 사용해, 5셀 고정 폭으로 팽창·수축하는 heartbeat를 굵고 밝게 표시한다. 별도 타이머·스레드·I/O·모델 호출·상태 저장·가짜 진행률은 만들지 않는다. 피드는 단계 그래프의 유효한 마지막 3건을 선택한 뒤 오래된 것부터 보여주며 각 항목은 공급자·라운드·단계, 기록된 대상 문서 계보와 정제 요약을 사용한다. workflow-v1 결과에 기록되지 않은 문서 계보는 추정하지 않는다.

- 공급자 프로세스가 응답을 반환했더라도 스키마 검증, 비밀값 제거, 산출물 원자적 저장과 상태 커밋이 끝나기 전에는 완료 요약으로 공개하지 않는다.
- `COMMITTED` 단계라도 산출물 해시와 해당 workflow의 단계 결과 스키마를 다시 통과한 항목만 피드 후보로 사용한다. 해시 또는 스키마가 손상된 항목은 제외하고 더 오래된 유효 항목으로 최대 3건을 채운다.
- 개요는 최신 결과를 처음 선택한다. `↑/↓` 또는 `J/K`로 이동하고 `D`로 선택한 한 건의 상세 화면을 열며 `P`는 `현재 AI 작업이 끝난 뒤 멈추기`를 정확히 한 번 요청한다. 실행 중 개요의 `Esc`는 AI를 몰래 중단하지 않고 `P`의 체크포인트 일시정지 방법을 즉시 안내한다.
- 작은 화면에서는 최근 완료 헤더, 현재 작업 또는 현재 위치, 현재 장벽 주변 최소 3개와 하단 행동을 먼저 보존한다. 가용 행이 늘어나면 검증된 최근 완료 최대 3건의 공백 우선 줄바꿈한 정제 요약과 구조화된 변경 집계를 줄이지 않고 단조롭게 확장한다. 최신 선택 항목을 우선하되 나머지 두 항목도 헤더와 의미 있는 본문을 균형 있게 유지하며, 표시할 안전 본문이 남아 있는 동안 큰 빈 영역을 만들지 않는다.
- 상단 `AI 작업 N/M`과 최근 완료 헤더의 `N/M`은 모두 전체 단계 그래프 기준이다. 활성 단계가 없으면 `지금 작업` 대신 `현재 위치`를 표시하고, 전체 실행 상태는 상단에서 한 번만 표시하며 하단은 별도 `다음 할 일` 영역으로 구성한다. 빨간색은 구조적 오류 행 또는 정확한 오류 상태에만 사용하고 정상 정제 요약의 단어 포함 여부로 정하지 않는다.
- 상세 화면은 선택한 결과 한 건만 표시한다. `PgUp/PgDn/Home/End`로 정제 요약과 변경 집계를 스크롤하고 `Esc`로 개요에 돌아간다. 실행 완료 화면의 `Enter`와 `Esc`는 모두 작업 메뉴로 돌아가며, 실행 중 `Enter`는 종료 동작으로 사용하지 않는다.
- `72×20`, `80×24`, `100×30`, `120×32`, `120×40`, `160×50`, `160×60`에서 각 프레임이 지정 높이보다 작고 각 줄이 터미널 폭보다 한 셀 작게 유지되어야 한다. 큰 화면으로 갈수록 실행 흐름 수와 안전한 최근 완료 본문 표시량이 줄어들지 않아야 하며 compact 화면과 진단 우선순위는 유지한다.
- 행동 집계는 0건 상태를 생략하고 화면에서는 `새 항목`의 반드시 해결·중요·참고, `의견 처리`의 수용·일부 수용·거부·보류·자료 필요·답변 필요, `문서 반영`의 반영·일부 반영·미반영·보류를 분리한다. 응답 수용을 실제 편집 반영이나 전체 합의로 표현하지 않는다.
- 내부 모드·단계·상태·중요도·처리 상태·반영 판단 값과 저장 스키마는 바꾸지 않는다. 사용자 화면에서만 쉬운 일상어로 매핑하고 알 수 없는 새 값은 숨기지 않고 정제된 원래 값을 표시한다.
- `context-batch-analysis`의 공급자 원요약은 공개하지 않고 검증·저장 완료만 알리는 일반화된 문구를 사용한다.
- 원시 stdout·stderr, 생성 중 텍스트, 전체 문서와 내부 사고 과정은 진행판에 표시하지 않는다.
- 진행 이벤트와 `diagnostics.jsonl`은 명시된 메타데이터 허용 목록만 사용한다. 진단 행은 `diagnosticId`, 고정 공개 요약, run·step·process·recovery·environment의 허용 필드와 모듈 내부 상대 stack frame만 가질 수 있다.
- 원문 공급자 출력, stdout·stderr 본문, 프롬프트·컨텍스트 팩·문서·모델 결과, 명령 인자, 환경변수 값, 인증정보, 절대 입력 경로, `Exception.ToString()`, 원시 stack과 임의 `Exception.Data`는 진행 이벤트, 진단 파일이나 화면에 기록하지 않는다. 이 금지는 run 생성 전, 성공·오류·재시도·재개, renderer와 TUI 폴백 경로에 모두 적용한다.
- 비밀 제거를 거친 공급자 응답 보존본이 필요한 경우에도 진단·이벤트가 아닌 별도 접근 제한 아티팩트로 저장하고 해당 본문을 이벤트 요약에 복제하지 않는다.
- 같은 장벽의 한쪽 단계만 완료되면 해당 공급자만 완료로 표시하고 장벽 전체는 진행 중으로 유지한다. 화면 공개가 다른 공급자의 프롬프트 의존 관계나 실행 순서를 바꾸지 않는다.
- 실제 모델 호출은 최종 계획을 확인할 수 있는 비리디렉션 대화형 입출력을 요구하며, 리디렉션된 라이브 실행은 공급자 호출 전에 차단한다. 대화형 호스트에서 VT가 없거나 창이 좁거나 렌더링이 실패하면 단계 전환과 해당 단계의 최신 확정 요약 한 건만 기록하는 ANSI 없는 축약형 누적 로그로 폴백하며 heartbeat에는 같은 요약을 반복하지 않는다.
- 오류·재시도·중단 복구·최종 renderer 실패에는 진행판, 누적 로그, 메뉴 복귀 화면과 명시적 `resume --live` 결과가 동일한 DF 코드·`diagnosticId`·writer의 실제 최종 진단 파일 경로를 표시한다. 작은 오류 화면에서는 실행 흐름과 최근 완료 본문보다 이 진단 참조를 우선한다.
- 프로세스 재개 시 이벤트 재생만 믿지 않고 `steps.json`과 검증된 단계 산출물에서 최근 피드와 화면을 복원한다. `workflow-v1`은 기존 결과 계약으로 읽고 저장 원본을 재작성하지 않으며, 이전 프로세스 종료로 `STARTED`에 남은 단계는 실행 잠금 획득 후 재개 가능 상태로 복구한다.
- 진행판 렌더러와 heartbeat observer 오류는 토론 실행, 단계 상태 또는 최종 결과를 실패시키지 않는다. 오류는 원문 예외 대신 고정 코드와 안전한 횟수만 한 번 기록하고, 전체화면을 유지할 수 없으면 중복 heartbeat가 없는 누적 로그로 폴백한다.

| 실행 상태 | 기본 메뉴 동작 |
|---|---|
| `AWAITING_USER` | 대기 중인 질문 보기, 쉬운 설명, 양쪽 비교, 답변, 보류 |
| `AWAITING_EVIDENCE` | 필요한 근거 안내, 입력 추가 또는 부분 완료 선택 |
| `PAUSED_USER` | 사용자 화면에는 `사용자 요청으로 멈춤`으로 표시하고, 사람이 읽을 수 있는 마지막 완료 작업과 앞으로 실행될 AI 작업을 보여준 뒤 재개 |
| `PAUSED_QUOTA` | 한도 원인과 재개 조건을 보여주되 API 과금 전환은 제안하지 않음 |
| `RESUMABLE_ERROR` | 실제 실행 가능한 단계와 남은 현재 입력 세대 재시도 예산이 있을 때만 실패 단계, 영향 범위와 안전한 재개 선택지 제공 |
| `FAILED_STAGE` | 재시도 소진 또는 복구 불가능한 단계 실패를 종료 상태로 표시하고 일반 재개를 숨김 |
| `COMPLETED`·`COMPLETED_PARTIAL` | 최종 결과 열기, 결과 폴더 열기, 요약 보기 |
| `CANCELLED` | 사용자 화면에는 `포기함`으로 표시하고 일반 재개를 숨기며, 기록 확인·복원·영구 삭제를 제공 |

사용자 결정은 쟁점 ID를 직접 입력하는 대신 질문 카드와 번호 선택으로 처리한다.

```text
결정이 필요한 사항 1/2

D-004: 데이터베이스 선택

Codex 권고: SQLite
Claude 권고: PostgreSQL
공동 권고: 초기 버전은 SQLite

[1] 공동 권고대로 진행
[2] SQLite 선택
[3] PostgreSQL 선택
[O] 선택지에 없는 내 의견 직접 입력
[M] 자세히 보기·추가 검토
[X] 결정 보류
```

- 쟁점 ID는 감사 추적을 위해 표시할 수 있지만 일반 흐름에서 입력을 요구하지 않는다.
- 답변 후 해석된 결정, 영향받는 산출물과 되돌리기 가능 여부를 확인받은 뒤 적용한다.
- 여러 질문이 있으면 최대 3개씩 처리하고 현재 위치와 남은 질문 수를 표시한다.
- 결과 열기는 기본 연결 프로그램으로 최종 Markdown을 열거나 Windows Explorer에서 결과 폴더를 여는 선택지를 제공한다.

### 15.6 고급 CLI와 자동화

다음 짧은 명령은 메뉴의 주요 진입점을 직접 연다.

```powershell
duoforge
duoforge new
duoforge resume
duoforge open
duoforge doctor
```

- 메뉴에서 만든 실행과 명시적 명령으로 만든 실행은 같은 상태·산출물·재개 규칙을 사용한다.
- 명시적 명령의 입력 오류는 대화형 메뉴를 강제로 열지 않고 원인, 올바른 예시와 종료 코드를 반환한다.
- 비대화형 자동 승인 옵션은 v1 이후에 검토하며, v1의 실제 모델 호출은 최종 실행 계획에 대한 명시적 사용자 확인을 요구한다.
- 기존 `dual-document --codex ... --claude ...`, `--codex-context`, `--claude-context`는 각각 A/B 정규 입력으로 변환하고 사용 중단 예정 경고를 반환하는 호환 별칭이다. 신규 매니페스트에는 정규 필드만 기록한다.
- 기존 프로젝트 입력 별칭 `--codex-project`, `--claude-project`도 향후 모드 4 활성화 시 프로젝트 A/B로 정규화하되 현재는 격리 게이트를 우회하지 못한다.

### 15.7 `doctor`

`doctor`는 다음을 확인한다.

- PowerShell 7 실행 여부
- Codex CLI 및 Claude Code CLI 설치와 버전
- `codex login`, `codex login status`, `claude auth login`, `claude auth status` 또는 지원 버전의 동등 기능 존재 여부
- 두 CLI의 로그인 상태, 만료 여부와 활성 인증 유형
- 활성 인증 방식이 구독인지 API 자격증명인지 신뢰성 있게 판별할 수 있는지
- 필수 실행 폴더의 읽기·쓰기 권한
- 한글과 공백이 포함된 경로 처리
- 값을 표시하지 않은 `ANTHROPIC_API_KEY`, `OPENAI_API_KEY` 및 공급자별 API 자격증명 환경 변수 존재 여부
- 대화형 Windows 세션에서 파일·폴더 선택창을 열 수 있는지 여부. 실패해도 경로 입력 방식이 가능하면 경고로 처리한다.
- doctor·모델 카탈로그·단계 호출이 사용하는 실제 실행 파일, 인증 home과 정제된 자식 환경이 동일한지 여부
- 카탈로그에 모델이 보이는 것과 실제 호출 가능성을 구분하고, 승인된 LIVE 성공 전에는 후자를 `UNVERIFIED`로 표시하는지 여부

v1의 기본 설정은 `subscriptionOnly=true`다. 이는 DuoForge가 API 키 인증을 사용하지 않는다는 뜻이며 계정 수준의 크레딧 사용까지 차단한다는 뜻은 아니다. 활성 CLI 인증이 API 방식이거나 공급자 CLI에서 API 인증을 우선하게 만드는 환경 변수가 감지되면 값을 출력하지 않고 실행을 차단한다. 특히 Claude Code는 `ANTHROPIC_API_KEY`가 있으면 구독 로그인보다 이를 우선할 수 있으므로 값의 유무만 검사하고 존재 시 실패 폐쇄한다. 인증 유형을 신뢰성 있게 판별할 수 없는 CLI 버전도 지원 불가로 차단한다. DuoForge는 환경 변수를 임의로 삭제하거나 인증 방식을 자동 변경하지 않으며 추가 비용이 절대 발생하지 않는다고 보장하지 않는다.

로그인 없음과 로그인 만료는 대화형 환경에서 즉시 실패 종료할 설정 오류가 아니라 15.2의 안내형 로그인으로 복구 가능한 상태다. 단, 두 구독 인증이 모두 확인되기 전에는 실행 계획 확정, 입력 전송 또는 모델 호출을 시작하지 않는다. 로그인 실행 자체는 공급자 CLI가 소유하는 별도 설정 단계이며 토론의 모델 호출 수나 라운드 수에 포함하지 않는다.

PRD 작성일 기준 Anthropic은 `claude -p`를 별도 Agent SDK 월간 크레딧으로 전환하려던 변경을 중단했으며, 현재는 기존 구독 사용 한도에서 차감된다고 안내한다. 이 정책은 변동 가능하므로 DuoForge는 이를 코드에 영구 가정으로 넣지 않는다. 최초 실행과 정책 확인 기한이 지난 실행에는 현재 공식 비용 정책 링크, 확인 일자와 구독 사용량 소진 가능성을 보여주고 사용자 확인을 받는다.

### 15.8 실행 전 확인

메뉴 마법사와 `start`는 모델 호출 전에 다음을 동일하게 표시한다.

- 선택한 모드와 라운드 수
- Codex와 Claude 각각의 선택 모델과 추론 정도
- 입력과 출력 절대 경로
- 각 공급자에게 전달될 파일 수와 크기 요약
- 제외될 파일과 제외 이유 요약
- 예상 최대 Codex·Claude 호출 수
- 입력 배치, 최초 분석, 교차 비평, 반박, 수정·최종화와 허용된 재시도를 구분한 공급자별 호출 계획
- 읽기·쓰기 권한 범위
- 활성 인증 방식과 과금 가능성 경고
- 마지막으로 확인한 공급자 비용 정책의 날짜와 공식 링크
- 재개용 실행 ID

대화형 실행은 사용자의 확인 후 시작한다. 확인 전에는 입력 인벤토리와 임시 계획 외에 모델 호출이나 최종 실행 상태 변경을 수행하지 않는다.

### 15.9 권장 내부 구성

```text
DuoForge CLI
├─ InteractiveShell
│  ├─ MenuRouter
│  ├─ PathPicker
│  └─ RecentPathStore
├─ CommandRouter
├─ AuthCoordinator
│  └─ CredentialInspector
└─ Orchestrator
   ├─ CodexAdapter
   ├─ ClaudeAdapter
   ├─ SnapshotManager
   ├─ ContextPackBuilder
   ├─ PromptBuilder
   ├─ SchemaValidator
   ├─ IssueManager
   ├─ StateStore
   ├─ SecurityGuard
   └─ ArtifactRenderer
```

- `InteractiveShell`과 `CommandRouter`는 입력을 수집하고 같은 오케스트레이터 요청으로 변환하는 얇은 표현 계층이다.
- `PathPicker`는 Windows 선택창, 직접 경로 입력과 검증 결과 표시를 담당하되 경로 안전 정책은 `SecurityGuard`에서 최종 판정한다.
- `RecentPathStore`는 편의용 경로 메타데이터만 저장하고 실행 상태나 입력 스냅샷을 저장하지 않는다.
- `AuthCoordinator`는 공식 공급자 로그인 프로세스를 한 번에 하나씩 전경에서 실행하고 성공·취소·실패 뒤 `CredentialInspector`의 재검사를 요청한다. 인증 프롬프트나 비밀값을 중계하지 않는다.
- `CredentialInspector`는 공급자별 상태 명령, 종료 코드, 환경 변수 이름과 공개 가능한 인증 유형만 판정하며 인증 파일 내용이나 토큰을 읽지 않는다.
- `Orchestrator`는 모드별 단계, 라운드 장벽, 사용자 게이트와 재개를 관리한다.
- 공급자 어댑터는 CLI 차이를 내부 공통 결과 형식으로 정규화한다.
- 각 공급자 호출에는 필요한 전체 문맥을 파일에서 다시 구성하며 공급자 세션 ID를 정합성 기준으로 사용하지 않는다.
- `StateStore`는 상태 파일을 원자적으로 교체하고 추가 전용 이벤트 로그를 유지한다.
- 실행 잠금 파일로 동일한 `runId`를 두 프로세스가 동시에 갱신하지 못하게 한다.
- 외부 프로세스 실행은 인수를 배열로 분리하는 안전한 프로세스 API를 사용한다. 프롬프트와 경로를 셸 문자열로 이어 붙이거나 `Invoke-Expression`으로 실행하지 않는다.
- 프롬프트 본문은 가능한 한 표준입력으로 전달하여 셸 기록과 프로세스 인수 노출을 줄인다.
- CLI 버전 번호만 고정하지 않고 `doctor`에서 필요한 명령과 플래그를 기능 탐지한다.

### 15.10 공급자별 기준 실행 프로필

아래 프로필은 PRD 작성 시점의 공식 CLI 옵션을 바탕으로 한 **구현 기준선**이다. 정확한 플래그 문자열보다 11.3의 공급자 실행 계약이 우선하며, 지원 버전마다 `doctor`와 격리 픽스처로 다시 검증한다.

**Codex 기준선**

```powershell
codex exec `
  --sandbox read-only `
  --ignore-user-config `
  --ignore-rules `
  --skip-git-repo-check `
  --ephemeral `
  --output-schema "<schema-path>" `
  --json `
  -
```

- 프롬프트는 표준입력으로 전달하고 프로젝트가 아닌 격리 작업 폴더에서 실행한다.
- doctor·모델 카탈로그·단계 호출은 동일하게 정규화한 실행 파일, 인증 home과 환경 허용·재정의 집합을 사용한다. 표시용 명령 이름이나 카탈로그 가시성만으로 실제 호출 가능성을 확정하지 않는다.
- 프로세스의 실제 작업 폴더를 새 비Git 격리 폴더로 지정하고 `--skip-git-repo-check`를 사용한다.
- `read-only`는 쓰기를 제한하지만 그 자체로 명령 실행 도구를 제거한다는 뜻은 아니다. 지원 Codex 버전에서 셸·외부 도구 표면을 제거할 수 없으면, 명령 실행과 범위 밖 읽기를 선제적으로 차단하는 별도 OS 수준 격리를 적용해야 한다.
- 위 두 방법 중 어느 것도 기능 검사로 증명하지 못하면 모드 4를 `DF-PREFLIGHT-3A-ISOLATION`으로 모델 호출 전에 차단한다. 실행 뒤 이벤트를 보고 위험한 명령이 없었다고 확인하는 방식만으로는 충분하지 않다.

**Claude 기준선**

```powershell
claude -p `
  --safe-mode `
  --strict-mcp-config `
  --tools "" `
  --no-chrome `
  --no-session-persistence `
  --output-format json `
  --json-schema "<inline-schema>"
```

- 빈 도구 목록과 엄격한 MCP 설정을 함께 사용하여 내장 도구와 MCP 도구를 모두 제거한다.
- `safe-mode`가 비활성화하는 사용자화 범위와 관리형 정책의 예외를 현재 버전에서 검사한다. 관리형 훅의 부재를 증명하지 못하면 모드 4를 `DF-PREFLIGHT-3A-ISOLATION`으로 차단한다. 단, Claude 프로세스 전체에서 자식 프로세스 생성·범위 밖 읽기·파일 쓰기를 선제 거부하는 OS 격리가 별도로 증명된 경우에만 진행할 수 있다.
- `--dangerously-skip-permissions`처럼 권한을 우회하는 옵션은 어떤 모드에서도 사용하지 않는다.

문서 모드 1~3에도 가능한 한 동일한 무도구·임시 세션 프로필을 적용한다. 모드 4는 여기에 프로젝트 밖 작업 폴더, 정제 컨텍스트 팩, OS 격리와 실행 전후 무결성 검증을 추가하며 현재는 격리 실패로 비활성이다.

## 17. 상태 모델과 재개

### 17.1 워크플로 버전과 호환성 경계

- 신규 실행은 매니페스트와 상태에 `workflowVersion: "workflow-v2"`를 기록한다.
- `workflowVersion` 필드가 없는 기존 실행은 `workflow-v1`로 간주한다.
- `workflow-v1 dual-document`는 기존 `inputs.codex/claude`, `roles.codex/claude`, `owner-response`, `owned-document-revision`, `codex-final.md`, `claude-final.md`와 당시 프롬프트 계약을 그대로 사용한다.
- `workflow-v2`는 `inputs.documentA/documentB`, `roles.documents.A/B`, `targetDocumentId`, `performedBy`와 신규 단계 계약을 사용한다.
- 레거시 필드는 읽기 경계에서만 정규형으로 변환하며 저장된 매니페스트, 단계 결과, 쟁점 원장과 완료 산출물을 재작성하지 않는다.
- 단계 그래프 생성, 추가 라운드, 사용자 결정 변경에 따른 무효화와 선택 재실행은 `workflowVersion`으로 분기한다.
- 기존 `duoforge-stage-v2` 프롬프트 계약 실행은 같은 계약으로 재개한다. 신규 실행은 `duoforge-stage-v3`처럼 구분된 계약을 사용하고 기존 실행을 일괄 승격하지 않는다.
- 구조화 결과 스키마도 워크플로 버전별로 선택한다. 레거시 스키마를 신규 필드 의미로 묵시적으로 해석하지 않는다.
- 신규 저장 세대는 `manifest` schema 4, `state` schema 2, `inventory` schema 2, `issue ledger` schema 2와 `steps` schema 2를 하나의 `duoforge-run-v2` 계약으로 묶는다. 어느 한 파일만 다른 세대이면 공급자 호출 전에 실패 폐쇄한다.
- 기존 `workflow-v1` 저장 세대와 초기 `workflow-v2` manifest schema 3 세대는 각자의 state/inventory/ledger/steps 버전 조합으로만 읽고 신규 세대로 부분 승격하거나 재작성하지 않는다.

### 17.4 재개 규칙

- `BLOCKED_PREFLIGHT`는 사용자가 환경 문제를 고친 뒤 같은 실행에서 사전 검사를 다시 수행할 수 있다.
- `FAILED_STAGE`, `SOURCE_DRIFT`, `COMPLETED`, `COMPLETED_PARTIAL`과 `QUESTION_LIMIT_REACHED`는 종료 상태이며 새 실행 없이 다시 열지 않는다. `CANCELLED`는 일반 재개할 수 없지만 정확한 복원 절차로만 `PAUSED_USER`에 전이할 수 있다.
- 각 단계의 입력 해시, 출력 경로와 완료 상태를 기록한다.
- 단계는 `STARTED → OUTPUT_CAPTURED → VALIDATED → COMMITTED`로 전이하며 `stepKey`, `inputHash`, `artifactHash`, `attemptId`를 기록한다.
- 단계의 `attemptCount`는 현재 입력 세대에서 사용한 시도 수, `totalAttemptCount`는 모든 입력 세대에 걸친 실제 공급자 호출 누계다. 사용자 결정·제약·추가 자료로 입력 세대가 바뀌면 `attemptCount`를 0으로 초기화하고 입력 세대를 증가시키되 `totalAttemptCount`는 감사 기록으로 보존한다. 이 필드가 없는 기존 저장 실행은 읽기 경계에서 기존 `attemptCount` 값으로만 정규화하며 호환 실행을 즉시 재작성하지 않는다.
- `resume`은 마지막 완료 단계 다음부터 시작한다. 답하지 않은 질문이 남아 있으면 명시적 라이브 재개도 공급자 호출 전에 차단하고, 현재 관문의 질문을 모두 답한 뒤에만 검토를 시작한다.
- 성공한 단계의 출력이 존재하고 해시가 맞으면 다시 호출하지 않는다.
- 출력이 없거나 해시·스키마가 손상되면 원인을 분리해 기록하고 해당 단계와 의존 단계만 감사 이력으로 보존한 뒤 재실행 대상으로 만든다. 쟁점 원장과 단계 산출물의 참조 무결성 충돌은 산출물 손상으로 오인해 무효화하지 않고 `DF-ISSUE-REFERENCE-INTEGRITY`로 실패 폐쇄한다.
- 실행 중 원본이 바뀌어도 기존 실행은 시작 시점 스냅샷으로 분석을 재개할 수 있지만, 모드 4 종료 무결성 검사에서 차이가 확인되면 `SOURCE_DRIFT`로 표시하고 현재 원본에 대한 완료 결과로 취급하지 않는다.
- 재개는 매니페스트의 `workflowVersion`과 프롬프트 계약을 먼저 확인한다. 이를 알 수 없거나 저장 산출물과 모순되면 신규 의미로 추정하지 않고 실패 폐쇄한다.
- 재개는 manifest/state/inventory/issue ledger/steps의 저장 세대, workflowVersion과 역할·주 입력 스냅샷 참조가 서로 일치하는지도 공급자 호출 전에 확인한다.
- 사용자가 최신 원본을 반영하려면 새 실행을 만들어야 한다.
- `Ctrl+C`는 긴급 중단으로 현재 자식 프로세스의 종료를 요청하고 마지막 완료 체크포인트를 보존한다.
- `P` 또는 명시적 일시정지는 현재 모델 호출을 끊지 않고 다음 호출 직전 체크포인트에서 멈춘다.
- 실행 포기는 감사 아티팩트를 보존한다. 복원은 포기한 실행에 한해 별도 확인과 실행 잠금 뒤 항상 `PAUSED_USER`로 전이하되 AI 작업을 시작하지 않는다. 영구 삭제는 포기한 실행에 한해 별도 확인과 경로·잠금 검증 뒤 전체 실행 폴더를 삭제한다.
- 출력 캡처 뒤 상태 커밋 전에 중단되면 기존 출력을 검증하여 승격하거나 격리한다.
- 공급자 호출 도중 종료되어 응답을 캡처하지 못한 경우에는 공급자가 실제 호출을 처리했는지 알 수 없으므로 재개 시 중복 사용량이 발생할 수 있음을 알린다.

## 18. 파일 및 데이터 구조

### 18.1 실행 디렉터리

기본 결과 루트는 `D:\Coding\APP-windows\DuoForge\results`이며, 사용자가 `--workspace` 또는 고급 설정의 Windows 폴더 선택창으로 다른 루트를 선택할 수 있다. 결과 루트가 없으면 첫 사용 시 생성하고 쓰기 권한을 검사한다. 생성하거나 쓸 수 없으면 실행을 시작하지 않고 원인과 다른 폴더 선택 동작을 제공한다. 어떤 경우에도 정규화한 결과 루트가 입력 문서 폴더나 프로젝트와 같거나 그 내부에 있으면 안 된다. 선택한 결과 루트 아래에는 실행 ID별 폴더를 만들어 원본과 이름 충돌 없이 전체 실행 기록과 최종 문서를 보존한다.

```text
<results-root>/
└─ <run-id>/
   ├─ manifest.json
   ├─ state.json
   ├─ events.jsonl
   ├─ diagnostics.jsonl        # 오류가 있을 때만 생성
   ├─ issues.json
   ├─ inputs/
   │  ├─ inventory.json
   │  ├─ snapshots/
   │  └─ context-packs/
   ├─ rounds/
   │  ├─ round-01/
   │  │  ├─ snapshots/
   │  │  ├─ responses-redacted/
   │  │  ├─ reviews/
   │  │  ├─ responses/
   │  │  └─ revisions/
   │  └─ round-02/
   ├─ decisions/
   │  ├─ pending.json
   │  └─ decisions.jsonl
   └─ final/
```

사용자용 최종 결과, 구조화 상태, 비밀정보 필터를 거친 모델 응답 보존본과 진단 레코드를 명확히 분리한다. 오류가 발생하면 실행 폴더의 `diagnostics.jsonl`에 append하고, run이 없거나 그 파일에 쓸 수 없으면 `%LOCALAPPDATA%\DuoForge\diagnostics\<diagnostic-id>\diagnostics.jsonl`로 폴백한다. 양쪽 writer 실패는 원래 오류를 가리지 않고 `DF-DIAGNOSTIC-WRITE`만 추가한다. 신규 실행은 사용되지 않는 `logs/`를 만들지 않으며 기존 실행·fixture의 `logs/`는 삭제하거나 재작성하지 않는다. `workflow-v1`의 기존 `raw-redacted/` 경로도 재개 호환성을 위해 그대로 읽고 신규 실행 디렉터리명으로 재작성하지 않는다.

예를 들어 공동 문서 실행 `run-20260727-001`의 기본 최종 문서는 `D:\Coding\APP-windows\DuoForge\results\run-20260727-001\final\PRD.md`에 저장한다. `--workspace`는 최종 파일 하나의 위치가 아니라 위 전체 실행 구조를 담을 결과 루트를 지정한다.

### 18.2 매니페스트

`manifest.json`은 최소한 다음을 기록한다.

- 실행 ID, 모드와 `workflowVersion`
- 생성·갱신 시각
- 입력 절대 경로의 안전한 표현과 스냅샷 해시
- 출력 경로
- 문서 유형과 라운드 수
- 문서 계보 역할 `roles.documents.A/B`, 단계별 `performedBy`와 호출 순서
- Codex 및 Claude CLI 버전
- Codex 및 Claude에 사용자가 선택한 모델명과 추론 정도
- 활성 인증 방식 유형
- 프롬프트 템플릿·계약 버전과 단계 결과 스키마 버전
- 포함·제외 규칙
- 예상 및 실제 호출 수
- 사용자 결정 목록

신규 매니페스트 schema 4는 `storageContractVersion`, state/inventory/issue ledger/단계 그래프/단계 결과의 명시적 버전을 기록한다. `inputs.documentA/documentB` 또는 공동 문서 입력은 원본 절대 경로나 본문이 아니라 `snapshotName`과 `sha256`의 안전한 참조로 저장하며, `roles`는 `inputs/inventory.json`의 역할과 정확히 일치해야 한다.

신규 매니페스트에는 `inputs.documentA/documentB`와 정규 필드만 기록한다. 인증 토큰, 비밀값, 원문 공급자 응답과 문서 본문은 기록하지 않는다. 레거시 별칭으로 시작했더라도 `CodexDocument/ClaudeDocument`나 공급자 소유 문서 필드를 신규 매니페스트에 쓰지 않는다.

## 19. 비기능 요구사항

### 19.1 안전과 보안

- 기본 권한은 최소 권한이며 모델 호출은 문서 작업에서도 가능하면 읽기 전용으로 수행한다.
- 입력 문서, 소스 코드, 주석, `AGENTS.md`, `CLAUDE.md`와 README의 지시문은 오케스트레이터 명령이 아니다.
- 모델 출력은 신뢰하지 않는 입력으로 취급하고 스키마와 허용 목록을 검증한다.
- 공급자 사용자 설정의 MCP, 훅, 플러그인, 스킬, 자동 메모리와 외부 도구가 실행에 개입하지 않도록 격리한다.
- 웹 검색, 브라우저, 컴퓨터 제어와 외부 커넥터는 모든 v1 모드에서 비활성화한다.
- 공급자 권한 우회 또는 위험한 전체 접근 옵션을 사용하지 않는다.
- 정규화한 절대 경로가 허용된 입력 및 출력 경계 안에 있는지 확인한다.
- 결과 루트는 입력 문서의 부모 폴더나 프로젝트 폴더와 같거나 그 내부에 둘 수 없다.
- 정션, 심볼릭 링크와 경로 순환을 탐지한다.
- 비밀정보 기본 제외 및 탐지 규칙을 제공한다.
- 전송 대상 미리보기와 공급자 전송 고지를 제공한다.

### 19.2 신뢰성과 복구

- 상태 저장은 임시 파일 작성 후 원자적 교체 방식으로 수행한다.
- 각 모델 호출은 타임아웃과 종료 코드를 가진다.
- 실패 원인, 마지막 체크포인트, 재시도 여부와 재개 명령을 기록한다.
- 부분 산출물을 최종 결과처럼 표시하지 않는다.
- 한쪽만 성공한 라운드를 완료로 판정하지 않는다.

### 19.3 재현성과 감사 가능성

- 모델 문장이 동일하게 재생된다고 보장하지 않는다.
- 대신 입력 해시, 프롬프트 버전, CLI 버전, 호출 순서, 역할, 필터링된 응답 보존본과 사용자 결정을 보존한다.
- 같은 실행의 각 결론을 당시 입력 스냅샷과 연결할 수 있어야 한다.

### 19.4 성능과 사용량

- 입력 인벤토리를 먼저 만들고 관련성 기준으로 컨텍스트를 분할한다.
- 파일을 조용히 누락하거나 자르지 않는다.
- 모델 호출 전에 예상 최대 호출 수를 표시한다.
- 실행 계획의 예상 최대 호출 수에는 기본 호출, 허용된 재시도와 형식 복구 호출을 모두 포함한다.
- 최대 라운드 및 재시도 상한을 코드 수준에서 강제한다.
- 계획기는 입력 배치, 최초 분석, 교차 비평, 반박, 수정·최종화와 단계별 1회 재시도를 모두 포함한 공급자별 최악 호출 수를 계산한다.
- 예상 실행 계획이 공급자별 호출 수, 호출 입력량, 문맥 사용률 또는 전체 실행 시간 상한을 넘으면 첫 모델 호출 전에 범위를 줄이도록 요청한다. 사용자가 범위를 줄이지 않으면 예측 커버리지를 보여주고 `COMPLETED_PARTIAL` 결과에 명시적으로 동의한 경우에만 부분 분석을 시작한다.
- 의미 배치의 봉투 오버헤드는 `CORE`와 분리해 예약하고, 완성된 단계 프롬프트가 호출당 상한 안에 있는지 실행 생성 시점과 소비 시점에 모두 검증한다.
- 부분 분석은 A/B와 각 문서에서 앞부분만 선택하지 않도록 결정론적으로 층화하고, 누락 섹션 ID·바이트·문서별 `CORE` 커버리지를 실행 계획과 최종 `COVERAGE.md`에 공개한다. `DOCUMENT_MAP`과 앞뒤 연결 범위의 중복 바이트는 커버리지로 계산하지 않는다.
- 모드 2·3의 부분 분석은 A와 B에 각각 최소 한 배치를 확보해야 한다. 호출 여유가 두 문서를 모두 덮지 못하면 `--allow-partial`이 있어도 preflight에서 차단한다.
- 설명 호출도 실행 예산에 포함하며 한도 도달 후에는 기존 설명을 보여주고 보류 또는 범위 조정을 안내한다.
- 문맥 한도 또는 파일 한도 때문에 분석이 불충분하면 전체 결론을 단정하지 않는다.

### 19.5 호환성과 사용성

- PowerShell 7을 기본 셸로 지원한다.
- UTF-8 한글 문서와 한글·공백이 포함된 Windows 경로를 처리한다.
- 오류 메시지는 실패 원인, 영향을 받은 범위와 다음 명령을 포함한다.
- 기술 용어가 포함된 사용자 질문에는 쉬운 설명을 함께 제공한다.
- 일반 사용자의 핵심 흐름은 `duoforge` 외의 명령, 내부 모드명, 실행 ID 또는 쟁점 ID를 외우지 않고 완료할 수 있어야 한다.
- 메뉴는 숫자와 문자 키만으로 사용할 수 있고 색상이나 방향키에만 의미를 의존하지 않는다.
- Windows 선택창을 사용할 수 없는 환경에서도 경로 붙여넣기와 명시적 CLI로 동일한 기능을 사용할 수 있어야 한다.
- 드래그 앤 드롭 경로의 바깥쪽 따옴표, 한글, 공백, 긴 경로와 UNC 경로를 처리한다.
- 화면 전환마다 현재 단계, 선택된 입력, 뒤로 가기와 취소 방법을 명확히 표시한다.

## 20. 오류 처리

| 오류 | 필수 동작 |
|---|---|
| CLI 미설치 | 설치가 필요한 도구와 확인 방법을 알리고 `BLOCKED_PREFLIGHT`로 차단 |
| 로그인 없음 | 대화형 환경에서는 공급자별 안내형 로그인을 제공하고, 비대화형 환경에서는 로그인 명령과 오류 코드를 출력한 뒤 `BLOCKED_PREFLIGHT`로 차단 |
| 로그인 만료 | 해당 공급자의 안내형 재로그인을 제공하고 기존 실행은 재개 가능한 `BLOCKED_PREFLIGHT`로 저장 |
| 로그인 취소·실패 | 모델을 호출하지 않고 최초 설정 화면에 남아 다시 시도, 수동 명령 보기 또는 종료를 제공 |
| 브라우저 자동 실행 실패 | 공급자 CLI가 제공하는 URL 복사·기기 코드·코드 붙여넣기 흐름을 보존하고 DuoForge가 비밀값을 중계하지 않음 |
| API 인증 우선 조건 감지 | 값을 숨기고 이유와 과금 가능성을 알린 뒤 `BLOCKED_PREFLIGHT`로 차단 |
| 구독 한도 도달 | `PAUSED_QUOTA`로 저장하고 API 과금으로 자동 전환하지 않음 |
| 모델 호출 시간 초과 | 동일 단계 1회 재시도까지 허용하고 소진하면 `FAILED_STAGE` |
| 구조화 출력 오류 | 형식 복구 전용 재요청 1회까지 허용하고 소진하면 `FAILED_STAGE` |
| 한쪽 호출 실패 | 상대 성공 결과를 보존하되 라운드는 미완료로 유지 |
| 입력 원본 변경 | 스냅샷 분석은 보존하되 모드 4는 `SOURCE_DRIFT`로 표시하고 새 실행 선택지를 알림 |
| 출력 손상 | 손상된 단계만 재실행하거나 새 실행을 안내 |
| 경로 중첩·링크 탈출 | 실행 전 차단하고 `BLOCKED_PREFLIGHT` |
| 모드 2·3 주요 문서의 부모 폴더 동일·중첩 | 각 폴더의 Markdown이 A/B 보조 문맥으로 자동 포함됨을 설명하고 어느 문서를 다시 선택할지 제공한 뒤 실행 전 차단 |
| 레거시 실행의 버전·산출물 불일치 | 신규 그래프로 추정하거나 재작성하지 않고 호환성 오류로 실패 폐쇄 |
| 모드 4 선택 | `DF-PREFLIGHT-3A-ISOLATION`과 현재 실패 이유를 표시하고 입력 전송·모델 호출 전에 차단 |
| 모드 4 원본 변경 감지 | 결과를 보존하되 `SOURCE_DRIFT`로 표시하고 현재 원본에 대한 성공을 주장하지 않음 |
| 입력 커버리지 부족 | `COMPLETED_PARTIAL`로 표시하고 제한을 최종 보고서 상단에 명시 |

`subscriptionOnly=true`인 v1에서는 API 인증이 실제로 우선하는 상태를 사용자 확인만으로 진행시키지 않고 사전 검사 실패로 처리한다. 사용자는 공급자 CLI를 구독 방식으로 다시 인증한 뒤 동일 실행을 재개할 수 있다.

## 21. 성공 지표

### 21.1 제품 가치

- 베타 사용자의 80% 이상이 최종 결과가 단일 AI 초안보다 유용하다고 평가한다.
- 모드 1 실행의 90% 이상이 3라운드 이내에 최종 문서 또는 명확한 사용자 질문 상태에 도달한다.
- 모드 2에서 추적 대상 A/B 항목의 95% 이상이 채택 상태, 이유와 반영 위치를 가진다.
- 모드 3에서 수용된 중요 아이디어의 95% 이상이 `sourceDocumentId`, `proposedByProvider`, 대상 문서와 반영 위치를 가진다.
- 사용자 질문의 80% 이상이 추가 외부 설명 없이 결정 가능한 수준이었다고 평가받는다.
- 신규 베타 사용자의 90% 이상이 별도 사용 설명서 없이 `duoforge` 홈 메뉴에서 첫 문서 실행의 최종 확인 화면까지 도달한다.
- 사전 로그인하지 않은 신규 베타 사용자의 90% 이상이 별도 명령 설명서 없이 안내형 로그인으로 두 구독 인증을 완료하고 홈 메뉴로 돌아온다.
- 베타 사용자의 90% 이상이 실행 ID나 쟁점 ID를 직접 입력하지 않고 진행 중인 작업 재개와 필수 결정을 완료한다.

### 21.2 신뢰성

- 정상 입력 실행의 95% 이상이 수동 파일 복구 없이 완료된다.
- 체크포인트 재개 테스트의 100%가 완료된 단계를 중복 호출하지 않고 복구된다.
- 생성된 Critical 및 Major 쟁점의 100%가 최종 상태 또는 사용자 대기 상태를 가진다.
- `workflow-v1` 재개 회귀 테스트의 100%가 기존 단계·파일 의미를 보존한다.
- 모드 4는 격리 게이트가 닫힌 동안 모델 호출 발생률 0%다.
- 향후 모드 4 격리 테스트에서 원본 프로젝트 변경 발생률은 0%여야 한다.
- 필수 산출물과 JSON 스키마 검증 통과율은 99% 이상이다.

### 21.3 효율

- 어떤 실행도 자동으로 3라운드를 초과하지 않는다.
- 같은 의미의 중복 쟁점 비율을 베타 기간에 10% 이하로 유지한다.
- 기본 설명, 답변, 재개 흐름은 홈 메뉴 진입 후 세 번 이하의 메뉴 선택으로 해당 동작을 시작할 수 있다.
- 공동 문서 기본 실행은 작업 종류, 입력 파일, Codex·Claude별 모델과 추론 정도, 최종 확인의 필수 결정을 안내형 메뉴에서 완료할 수 있다.
- 반복·자동화 사용자는 메뉴와 기능적으로 같은 실행을 하나의 명시적 `start` 명령으로 시작할 수 있다.

## 22. 출시 수용 시나리오

### 22.1 공통 시나리오

1. 유효한 입력과 사전 인증되었거나 안내형 로그인으로 인증을 완료한 두 CLI로 메뉴 또는 명시적 CLI에서 실행을 시작할 수 있다.
2. 2라운드와 3라운드 설정이 정확히 동작하며 상한을 넘지 않는다.
3. 매 단계 후 상태와 산출물이 저장된다.
4. 강제 종료 후 마지막 완료 체크포인트부터 재개한다.
5. 재개 시 완료한 모델 단계를 다시 호출하지 않는다.
6. 한쪽 모델 실패, 시간 초과, 구조 오류와 구독 한도 초과를 각각 안전하게 중단·재개한다.
7. 사용자 질문 상태에서 프로그램을 종료한 뒤 설명 또는 답변을 입력하고 완료할 수 있다.
8. 공백과 한글이 포함된 Windows 경로 및 UTF-8 문서를 정상 처리한다.
9. 입력 변경 시 기존 스냅샷과 새 원본을 섞지 않는다.
10. Critical 미해결 쟁점은 질문 또는 실패 사유 없이 완료 상태가 될 수 없다.
11. 가짜 공급자 어댑터를 사용한 상태 머신, 스냅샷, 스키마, 오류와 재개 테스트는 오프라인에서 실행할 수 있다.
12. 실제 Codex·Claude 호출이 필요한 E2E 테스트는 명시적 동의 없이는 실행되지 않으며 실행 전에 구독 사용량 소비 가능성을 표시한다.

14. 모드 2·3은 문서 A/B가 모두 있어야 하며 같은 폴더·중첩 폴더·입력 내부 결과 루트를 모델 호출 전에 차단한다.
15. 모드 2·3의 각 문서 폴더 보조 Markdown은 해당 A/B 계보 문맥에만 한 번 포함된다.

21. 구조화 결과의 공급자, 단계 유형과 대상 문서 불일치는 실패 폐쇄한다.

### 22.3 메뉴 및 사용성 시나리오

1. PowerShell 7의 대화형 터미널에서 인수 없이 `duoforge`를 실행하면 홈 메뉴가 열린다.

3. 새 작업 마법사는 네 목적을 표시하고 모드 1~3은 각각 `shared-document`, `document-merge`, `dual-document`로 매핑한다.
4. 모드 4는 `[4] 두 프로젝트 비교하기 — 비활성화`로 표시되며 선택하면 `DF-PREFLIGHT-3A-ISOLATION`으로 모델 호출 전에 차단된다.
5. Codex 또는 Claude에 사전 로그인하지 않은 상태에서도 최초 설정 화면에서 각 공급자의 공식 로그인을 시작할 수 있다.
6. `Codex 로그인 시작`은 `codex login`을 실행하고 종료 후 `codex login status`로 ChatGPT 구독 인증을 다시 확인한다.
7. `Claude 로그인 시작`은 `claude auth login`을 실행하고 종료 후 `claude auth status`로 Claude 구독 인증을 다시 확인한다.
8. 로그인 중 이메일, 비밀번호, 브라우저 코드, 토큰과 API 키가 DuoForge 입력·로그·상태·매니페스트에 나타나지 않는다.
9. 한 공급자만 로그인에 성공하면 성공 상태를 보존하고 실패한 공급자만 다시 시도할 수 있으며 모델 호출은 시작하지 않는다.
10. 사용자가 로그인을 취소하면 모델 호출 없이 다시 시도, 수동 명령 보기 또는 종료를 선택할 수 있다.
11. 두 공급자의 저장된 구독 인증이 유효한 후속 실행은 브라우저 로그인 없이 홈 메뉴로 진행한다.
12. 인증이 만료되면 해당 공급자만 안내형 재로그인하고 성공 후 사전 검사 또는 마지막 체크포인트로 돌아간다.
13. API 키·토큰 또는 API 인증 우선 조건이 있으면 값 없이 변수 이름과 과금 가능성을 알리고 자동 삭제·로그아웃 없이 차단한다.
14. 리디렉션된 표준입력이나 비대화형 환경에서는 로그인 프로세스나 브라우저를 시작하지 않고 사전 인증이 없으면 복구 명령과 오류 코드로 종료한다.
15. 공동 문서 기본 실행은 내부 모드명, 실행 ID와 출력 경로를 입력하지 않고 작업 종류, 입력 파일, Codex·Claude별 모델과 추론 정도, 최종 확인으로 시작한다.
16. 파일과 폴더를 Windows 선택창으로 선택할 수 있고, 선택창을 사용할 수 없는 환경에서는 경로 입력으로 전환한다.
17. Explorer에서 끌어놓은 따옴표·한글·공백 포함 파일과 폴더 경로가 올바른 절대 경로로 정규화된다.
18. 최근 경로에서 삭제·이동되었거나 접근할 수 없는 항목을 선택하면 오류 원인과 다시 선택 동작을 제공한다.
19. 모드 2·3의 두 주요 문서가 같은 폴더 또는 중첩 폴더에 있으면 자동 보조 문맥 규칙을 설명하고 잘못된 문서만 다시 선택할 수 있다.
20. 모드 2·3의 분리된 각 문서 폴더에서 자동 포함할 Markdown 목록·크기·제외 이유를 실행 전에 확인할 수 있다.
21. 동일·중첩 프로젝트와 입력 문서 폴더·프로젝트 내부 결과 루트는 메뉴와 명시적 CLI에서 똑같이 차단된다.
22. `AWAITING_USER` 실행을 홈 메뉴에서 선택하면 쟁점 ID 입력 없이 질문 카드, 쉬운 설명, 양쪽 비교, 답변과 보류를 사용할 수 있다.
23. 여러 진행 중인 실행이 있을 때 최근 갱신 순 목록에서 선택하며 모호한 실행을 자동 재개하지 않는다.
24. 완료 실행에서 최종 문서와 결과 폴더를 열 수 있다.
25. 같은 입력과 설정을 사용한 메뉴 실행과 명시적 CLI 실행이 같은 실행 계획, 검증 규칙과 산출물 구조를 만든다.
26. 뒤로 가기, 선택창 취소와 실행 전 취소는 모델 호출이나 확정 실행 생성을 유발하지 않는다.
27. 기본 결과 루트는 `D:\Coding\APP-windows\DuoForge\results`이며 고급 설정 또는 `--workspace`로 다른 안전한 폴더를 선택할 수 있다.
28. 새 실행은 두 공급자의 모델과 추론 정도를 모두 선택해야 하며, 라이브 재개 화면은 저장된 네 값을 다시 표시하고 누락된 이전 실행을 차단한다.
29. 공통 메뉴에서 `↑/↓` 순환, `Home/End`, `Enter`, `Esc`, 숫자·영문 단축키가 동작하고 선택한 비활성 항목의 이유가 보인다. 색상 지원 시 선택 항목 본문과 바로 아래 설명은 서로 다른 색이며, 무색 환경에서는 `>`와 들여쓰기로 구분된다.
30. 권장 모델이나 분석 깊이에 처음 커서가 있어도 `Enter` 또는 단축키로 확정하기 전에는 선택값이 생기지 않는다.
31. `PROVIDER_TICK`이 500ms 단위로 전달한 프레임 번호에 따라 5셀 heartbeat가 결정론적으로 팽창·수축한다. Unicode·ASCII 폴백의 폭이 같고, 경과 시간 표시는 초 단위를 유지하며, 추가 타이머·공급자 호출·상태 쓰기를 만들지 않는다.
32. `72×20`, `80×24`, `100×30`, `120×32` 개요에서 높이별 1·2·2·3건이 펼쳐지고 모든 줄과 행이 프레임 경계 안에 남는다.
33. 상세 화면은 선택한 최근 결과 한 건만 보여주며 스크롤·개요 복귀·기존 `P` 일시정지가 함께 동작한다.
34. 비대화형 메뉴 폴백과 정확한 `LIVE`, `PARTIAL`, `ROUND`, `APPLY` 확인 계약은 유지되고 원시 출력·생성 중 텍스트·전체 문서·프롬프트·모델 응답 원문이 화면에 나타나지 않는다.
35. 현재 관문의 모든 질문에 답하면 최종 문서·검증을 다시 수행하고 새 사용자 결정이 있을 때만 다음 관문을 연다. 새 질문이 없으면 즉시 완료하며, 최초 관문을 포함한 세 번째 검토 뒤에도 새 질문이 생기면 네 번째 관문 없이 `QUESTION_LIMIT_REACHED`로 질문과 결과를 보존한다.
36. 이전 답변 변경 목록과 새 답변 선택 화면에서 대상 문서·질문·핵심 쟁점·현재 답변을 독립 섹션으로 확인할 수 있고, 긴 본문은 끝까지 보존된다. 신규 기록은 질문 제목·문장을 보존하며 기존 기록은 쟁점·선택지로 복원했다는 안내와 함께 표시된다.
37. 네 지원 프레임의 기본 질문 카드는 제목과 본문을 분리한 채 높이 안에서 핵심 쟁점·제안·요청을 우선해 표시하고, 질문 전체 보기는 모든 폭에서 긴 구조화 필드의 끝과 선택 결과까지 생략 없이 표시한 뒤 답변을 기록하지 않고 결정 화면으로 돌아올 수 있다. 추가 자료 요청도 선택 뒤 핵심 쟁점과 필요한 자료의 끝까지 표시한다.
38. `72×20`, `80×24`, `100×30`, `120×32`의 질문·메뉴·CLI 보고서·LIVE·오류 대표 화면은 색상을 제거해도 섹션과 상태가 구분되고, 모든 긴 필드·목록·명령의 이어진 줄이 소속 본문 시작 열에 맞으며 최대 폭이 `width - 1`을 넘지 않는다.
39. 포기한 작업은 정확한 `RESTORE`에서만 `PAUSED_USER`로 복원되고, 취소·오타·리디렉션·비대화형 무확인은 상태·이벤트·파일과 공급자 호출을 만들지 않는다.

- 향후 모드 4 실행 전후 원본 프로젝트의 오케스트레이터 파일 인벤토리와 SHA-256이 동일해야 한다.
- 출력 경로 중첩, 동일 입력 경로, 정션 및 심볼릭 링크 탈출을 차단한다.
- 대상 프로젝트의 코드, 빌드, 테스트, 패키지 및 개발 서버 명령을 실행하지 않는다.
- 모델 출력의 명령이나 임의 경로를 다음 동작으로 직접 사용하지 않는다.
- 공급자 사용자화, MCP, 훅, 플러그인과 웹·브라우저 도구가 비활성화되었음을 기능 검사로 확인한다.
- 실제 공급자 E2E에서 도구·명령·웹·MCP 호출 이벤트가 0건이며, 모드 4는 이를 선제 차단하는 무도구 표면 또는 OS 격리가 검증될 때까지 비활성이다.
- 빈 비Git 격리 폴더의 Codex E2E가 성공하고 상위 프로젝트의 지시 파일을 읽지 않는다.
- 파일 쓰기를 시도하는 Claude 관리형 훅 픽스처가 모델 시작 전에 차단되거나 OS 격리에서 거부된다.
- API 자격증명 감지 시 비밀값을 출력하지 않고 과금 가능성을 고지한다.
- 안내형 로그인에서 이메일, 비밀번호, 인증 코드, 토큰, API 키와 공급자 인증 파일 내용이 DuoForge 프로세스의 입력·로그·상태·매니페스트에 기록되지 않는다.
- 로그인 없음·만료·취소·실패와 한쪽만 로그인된 상태에서 실제 모델 호출과 입력 전송이 0건이다.
- API 인증 우선 조건에서 환경 변수 삭제, 공급자 로그아웃 또는 인증 방식 변경을 사용자 승인 없이 수행하지 않는다.
- 성공·오류·재시도·재개·TUI 폴백의 로그와 진행 이벤트에 원문 공급자 출력, 문서·프롬프트·컨텍스트 내용과 비밀값이 0건이다.
- 모드 4 선택은 `DF-PREFLIGHT-3A-ISOLATION`으로 모델 호출과 입력 전송 전에 차단된다.
- Critical 미해결 쟁점을 숨긴 채 `COMPLETED`로 종료하지 않는다.
- 미해결 Critical에 모델이 `blocking=false`를 제안하는 오류·악성 픽스처에서도 오케스트레이터가 `blocking=true`를 강제하고 완료를 차단한다.

## 23. 구현 단계

### 단계 0: 기존 기준선과 안전 게이트 고정

- 기존 `workflow-v1 shared-document/dual-document` 동작과 52개 오프라인 테스트를 기준선으로 보존한다.
- 현재 3A 격리 스파이크의 범위 밖 읽기·자식 프로세스 차단 실패를 유지하고 모드 4 활성화에 착수하지 않는다.
- 작업 시작 전과 각 주요 슬라이스 뒤 `tests/Run-Tests.ps1` 전체 회귀를 실행한다.

### 단계 1: 요구사항과 용어 고정

- 네 화면 모드, 내부 ID, A/B 계보와 공급자 작업자 분리를 문서·도움말 용어로 고정한다.
- 공급자 의견을 뜻하는 정상 용례와 공급자-문서 소유 결합 용례를 구분하여 정적 검색한다.

### 단계 2: 정규 입력 모델과 레거시 어댑터

- `document-merge`, `DocumentA/B`, `inputs.documentA/documentB`, `roles.documents.A/B`를 추가한다.
- 모드 2·3에 동일한 비중첩 폴더·Markdown 자동 포함·출력 경계 검증을 적용한다.
- 레거시 `CodexDocument/ClaudeDocument`, `--codex/--claude`와 컨텍스트 별칭을 A/B로 변환하고 경고한다.
- 컨텍스트 배치가 A/B 주요 문서와 보조 문맥을 중복 없이 포함하는지 테스트한다.

### 단계 3: 버전된 실행·스냅샷 호환성

- `workflowVersion`, 프롬프트 계약과 단계 결과 스키마 버전을 기록한다.
- `workflow-v1` 인벤토리·단계 그래프·파일명을 그대로 읽고 재개하는 경로를 보존한다.
- 기존 실행을 `workflow-v2` 의미로 묵시적으로 재구성하지 않는 회귀 테스트를 추가한다.
- 직렬화된 workflow-v1 저장 fixture로 누락 그래프의 v1 복원, v2 전용 프롬프트 필드 비노출, 확정 단계 미호출, v1 최종 파일과 원장 유지 및 fixture 해시 불변을 검증한다.

### 단계 4: 모드 2 `document-merge`

- 호출 계획, `independent-merge-draft`, 교차 검토·응답·교대 합성·최종 검증을 구현한다.
- 같은 A/B 스냅샷 장벽과 두 독립 후보의 비가시성을 테스트한다.
- 최종 C와 A/B 출처 추적표를 렌더링한다.

### 단계 5: 모드 3 공급자-문서 분리

- 신규 워크플로에서 `owner-response`, `owned-document-revision`을 사용하지 않는다.
- 양쪽 공급자의 A/B 전체 검토, 문서별 쟁점, 편집 담당 교대와 두 수정본 장벽을 구현한다.
- 문서별 최종 검증과 선택 재실행 의존성을 구현한다.
- `workflow-v1 dual-document`에는 기존 단계와 파일명을 유지한다.

### 단계 6: 메뉴·CLI·진행판과 비노출 경계

- 네 모드를 표시하고 모드 4는 비활성 이유와 오류 코드를 명확히 보여준다.
- 파일 선택·미리보기·오류·진행 단계 이름을 문서 A/B 기준으로 바꾼다.
- 실행별 진단·진행 이벤트의 메타데이터 허용 목록, run/local 폴백과 공급자 원문·문서 내용·비밀값 0건 회귀를 추가한다.

### 단계 7: 전체 검증과 문서화

- README, PRD, 구현 계획, 도움말, 메뉴, 오류와 진행판 용어를 일치시킨다.
- 가짜 공급자 E2E를 모드 1·2·3 각각 2라운드로 검증한다.
- `workflow-v1` 조회·재개, 신규 스키마와 레거시 별칭 회귀를 검증한다.
- 라이브 공급자 E2E는 전체 로컬 테스트 통과 뒤 기존 명시적 확인 절차로 별도 수행한다.
- 모드 4가 `DF-PREFLIGHT-3A-ISOLATION`으로 계속 실패 폐쇄되는지 검증한다.

| 최근 경로에 민감한 위치 노출 | 로컬 사용자에게 프로젝트 위치 노출 | 경로 메타데이터만 저장, 로컬 보호, 개별·전체 삭제 제공 |
| 모드 2·3 A/B 문맥 혼합 | 한 문서 보조 문맥에 다른 계보 문서가 의도치 않게 포함 | 동일·중첩 부모 폴더 차단, 자동 포함 목록 미리보기, A/B별 폴더 구성 안내 |
| 공급자와 문서의 재결합 | 신규 실행에서 레거시 소유권 의미가 부활 | 정규 A/B 모델, `performedBy` 분리, 스키마·용어 회귀 검사 |
| 레거시 실행의 묵시적 승격 | 기존 산출물·재개 의미 손상 | `workflowVersion` 분기, 읽기 경계 어댑터, 저장 원본 불변 테스트 |
| 로그·이벤트 본문 노출 | 문서·공급자 출력·비밀값 유출 | 메타데이터 허용 목록, 본문 금지, 성공·오류·재개·폴백 회귀 검사 |
| 공급자 로그인 명령·출력 변경 | 최초 설정이나 인증 유형 판정 실패 | 버전별 기능 탐지, 상태 명령 종료 코드·구조화 출력 검증, 지원 버전 매니페스트 |
| 인증 비밀값이 DuoForge에 노출 | 계정 탈취 또는 민감정보 로그 유출 | 공급자 CLI가 직접 브라우저 인증, 비밀 입력 비수집, 인증 파일 미열람, 로그 회귀 검사 |
| API 키가 구독 로그인보다 우선 | 의도하지 않은 API 과금 | 환경 변수 이름만 탐지, 실패 폐쇄, 자동 삭제·로그아웃 금지, 재검사 안내 |

## 25. 출시 완료 정의

DuoForge v1은 다음 조건을 모두 충족할 때 완료된 것으로 본다.

- 화면에 네 모드가 구분되어 있고 활성 문서 모드 1~3의 필수 흐름과 산출물이 구현되어 있다.
- 모든 P0 기능 요구사항과 안전 출시 게이트가 통과한다.
- `duoforge` 홈 메뉴, 새 작업 마법사, Windows 선택창·경로 입력 대체 흐름과 상태 기반 이어하기가 구현되어 있다.
- 사전 로그인하지 않은 사용자가 안내형 공식 로그인으로 두 구독 인증을 완료하고 홈 메뉴 또는 시작하려던 작업으로 돌아갈 수 있다.
- 로그인 없음·만료·취소·실패·API 인증 우선 상태에서는 어떤 입력 전송이나 모델 호출도 발생하지 않는다.
- DuoForge가 인증 비밀값과 공급자 인증 파일 내용을 입력받거나 저장하지 않음이 테스트로 확인된다.
- 일반 사용자가 내부 모드명, 실행 ID와 쟁점 ID를 입력하지 않고 기본 실행·결정·재개·결과 열기를 완료할 수 있다.
- 메뉴와 명시적 CLI의 동일 입력이 같은 검증, 실행 계획, 상태 전이와 산출물 구조를 사용한다.
- 공통 메뉴의 커서·Enter 조작, 비대화형 줄 입력 폴백과 권장 항목의 명시적 확정이 검증된다.
- 5셀 LIVE heartbeat, 높이별 최근 완료 개요와 단일 상세 스크롤이 네 지원 프레임에서 폭·높이·비노출 계약을 지킨다.
- 모드 2·3에서 주요 문서 A/B 폴더 분리와 보조 Markdown 자동 포함 규칙이 메뉴·명시적 CLI 모두에서 동일하게 적용된다.
- 모드 2는 A/B를 동등 출처로 사용하여 C 하나와 출처 추적표를 만든다.
- 모드 3은 공급자 소유권 없이 A/B 계보를 유지하여 A'/B'를 만든다.
- 신규 실행 데이터에서 문서 ID와 공급자 작업자가 분리되고 `workflow-v2`가 기록된다.
- `workflow-v1` 실행은 기존 단계·파일·프롬프트 의미로 조회·재개되고 저장 원본이 재작성되지 않는다.
- 사용자 질문, 상세 설명, 답변, 보류와 재개가 동작한다.
- 기본 2라운드 및 최대 3라운드 제한이 강제된다.
- 원본 문서와 프로젝트가 모든 정상·오류 테스트에서 보존된다.
- 모드 4는 격리 게이트가 충족될 때까지 `DF-PREFLIGHT-3A-ISOLATION`으로 모델 호출 전에 차단된다.
- 재개 테스트가 완료된 단계를 중복 호출하지 않는다.
- 구독 한도 또는 인증 오류 시 상태와 결과를 잃지 않는다.
- 최종 산출물의 주요 결론을 입력 근거와 쟁점 이력으로 추적할 수 있다.
- 진단 파일, 진행 이벤트와 화면에 원문 공급자 출력, 문서·프롬프트·컨텍스트 내용, 명령·환경·인증 값과 비밀값이 기록되지 않으며 모든 진단 행을 Depth 100으로 재파싱할 수 있음이 테스트로 확인된다.
- 설치, 최초 실행, 네 화면 모드의 사용법·활성 상태와 제한사항이 문서화되어 있다.
