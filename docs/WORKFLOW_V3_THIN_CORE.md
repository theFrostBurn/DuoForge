# workflow-v3 얇은 자동 코어

상태: 구현 기준, 2026-08-02

## 결정

신규 문서 실행은 `workflow-v3`와 `thin-core-v1`을 사용한다. 기존
`workflow-v1`·`workflow-v2` 저장 실행은 원래 그래프와 계약으로만
조회·복구하며 읽기만으로 재작성하거나 승격하지 않는다.

기본 그래프는 같은 불변 입력을 서로 보지 않고 처리하는 Codex·Claude 독립
결과 각 1회, 지정 통합 담당 1회, 통합 담당이 아닌 AI의 최종 검증 1회다.
최종 검증에 Critical 또는 차단 Major 지적이 있을 때만 통합 담당의 최종 수정
1회를 연다. 자동 호출은 기본 4회, 최대 5회이며 추가 자동 토론 라운드는 없다.

## 결과 경계

공급자는 `primary`와 선택적 `metadata`만 반환한다. `primary.documents`는 앱이
제공한 출력 슬롯 순서의 Markdown 배열이고 최종 검증에서는 `approved`만
반환한다. `stage`, `provider`, `performedBy`, 문서 ID, 쟁점 ID는 공급자
스키마에 없으며 실행 그래프와 순서를 사용해 앱이 로컬에서 부착한다.

정규 단계 계약 정의 하나가 provider JSON Schema와 runtime validator를
생성한다. 필수값·형식·허용 개수와 주 결과/부가 결과의 실패 범위는 그 정의에만
둔다. `primary`가 유효하면 질문 선택지나 원장 후보 같은 `metadata` 오류는
해당 항목만 격리하고 문서와 공급자 호출을 보존한다. 격리된 질문은 표시하지
않고 자유 입력 경로를 유지한다.

## 복구 경계

사용자에게는 메뉴와 CLI 모두 `복구 준비` 하나만 제공하고 정확 확인어는
`RECOVER` 하나만 사용한다. 내부 원인 분류는 일반 재시도, 시간 한도, 입력
크기, 참조, 프로젝트 계약 결함으로 유지하되 사용자 명령·상태·확인어를
추가하지 않는다.

복구 준비는 실행 잠금 안의 원자적 provider 0-call 트랜잭션이다. 실제 AI
호출은 별도의 정확한 `LIVE` 확인을 다시 요구한다. 프로젝트 계약 결함은
`manualRetryCount`나 사용자 복구 허용량을 소비하지 않으며, 이미 일어난 실제
호출의 `totalAttemptCount` 감사 누계만 보존한다.

## 안전 불변식

- 한쪽 독립 호출 실패를 다른 한쪽 결과만으로 완료하지 않는다.
- 완료된 단계와 유효한 주 문서는 재개·메타데이터 격리 때문에 재호출하지 않는다.
- 원본 스냅샷, 공급자별 호출 상한, 자동 모델 대체 금지와 비노출 경계를 유지한다.
- 복구 준비 전 이탈·오타·비대화형 무확인은 파일 변경과 provider 호출이 0건이다.
- 저장된 v1/v2 실행과 현재 실패 실행을 v3로 묵시적으로 마이그레이션하지 않는다.
