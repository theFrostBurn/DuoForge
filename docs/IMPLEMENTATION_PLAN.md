# DuoForge 구현 계획

기준 문서는 `require/PRD.md` v1.12다. 구현은 기존 실행 의미를 보존하는 테스트 우선 수직 슬라이스로 진행했다.

상태: 문서 모드 확장 Beta, `workflow-v3/thin-core-v1`, 통합 복구, 실행별 안전 진단, 공통 터미널 화면 문법과 단일 `REVIEW_REPORT.md` 최종 보고서까지 구현했다. workflow-v3는 검토 요약·결정·채택/거절 정보를 하나로 통합하고 모드 2의 A/B 출처 추적과 모드 3의 A′/B′ 비교만 조건부 절로 추가한다. 신규 작업은 라운드를 선택하지 않고 내부 `maxRounds=1`의 기본 4회·조건부 최대 5회 고정 그래프를 사용하며, 2~3라운드는 저장된 workflow-v1/v2 호환 계약에만 적용한다. 현재 사용자 복구 표면은 메뉴의 단일 `복구 준비`와 CLI `recover`, 정확 확인어 `RECOVER`이며 아래 과거 슬라이스의 `repair-*`·`REPAIR`는 당시 구현 기록이자 내부 v1/v2 호환 어댑터 이름일 뿐 현재 사용법이 아니다. 모드 1~3의 기존 실제 공급자 E2E는 시점 증거로 보존하고 현재 동작은 전체 PowerShell 7 오프라인 회귀로 검증한다. 모드 4는 3A 격리 게이트 실패로 계속 비활성이다. 아래의 개별 테스트 수치는 각 슬라이스 완료 당시의 역사적 기준선이며 현재 전체 테스트 수를 뜻하지 않는다.

## 확정 제품 모델

| 화면 모드 | 내부 ID | 입력 | 결과 | 활성 상태 |
|---|---|---|---|---|
| 1. 컨셉으로 공동 문서 만들기 | `shared-document` | brief 또는 컨셉 C | 공동 문서 C' | 활성 |
| 2. 두 문서를 하나로 합의하기 | `document-merge` | 문서 A/B와 각 보조 Markdown | 합의 문서 C와 출처 추적표 | 실제 E2E 통과 |
| 3. 두 문서를 각각 개선하기 | `dual-document` | 문서 A/B와 각 보조 Markdown | 개선 문서 A'/B' | 실제 E2E 통과 |
| 4. 두 프로젝트 비교하기 | `dual-project-audit` | 프로젝트 A/B | 비교 결과 | 격리 실패로 비활성 |

- A/B는 공급자나 최초 작성자가 아니라 실행 안의 안정적인 문서 계보다.
- Codex와 Claude는 교체 가능한 검토자·응답자·편집자·합성자·검증자다.
- 단계의 `performedBy`는 감사용 작업 할당이며 문서 소유권을 뜻하지 않는다.
- 기존 내부 ID와 완료·재개 가능한 실행의 의미를 바꾸지 않는다.

## 슬라이스 9: 의미 기반 대용량 문맥 배치

### 확정 범위와 호환 경계

- 1차 목표는 모드 2·3의 대용량 Markdown을 의미 단위로 나누고, 각 배치가 전체 문서에서 차지하는 위치와 앞뒤 연결 문맥을 함께 전달하는 것이다. 모드 1의 기존 대용량 입력도 같은 분할기의 회귀 보호를 받는다.
- 신규 모델 호출, 새 토론 단계와 배치별 교차 비평은 추가하지 않는다. 현재 공급자별 `context-batch-analysis` 1회와 이후 전체 토론 그래프를 유지한다.
- 신규 실행은 `context-plan.schemaVersion=2`, `segmentationPolicy=semantic-markdown-v1`, `envelopePolicy=document-map-extractive-bridge-v1`을 기록한다.
- 기존 `context-plan.schemaVersion=1`, workflow-v1과 초기 workflow-v2 저장 실행은 읽기·조회·재개만 지원하고 분할 파일이나 저장 메타데이터를 재생성·마이그레이션하지 않는다.
- 바이트는 의미 분할의 기준이 아니라 호출 입력의 강제 상한과 최후 폴백으로만 사용한다.

### 테스트 우선 구현 순서

1. 현재 바이트/줄바꿈 분할의 한계를 고정하는 실패 회귀를 추가한다. 제목과 본문, fenced code, 표·목록, 서문·결론이 분리되지 않아야 하는 예시와 모드 2·3 강제 대용량 가짜 공급자 fixture를 먼저 만든다.
2. Markdown 구조 맵을 만든다. ATX/Setext 제목, 제목 경로, 서문, 완결된 문단·목록·표·fenced code를 인식하고 각 원본 스냅샷에 안정적인 섹션 ID, 순서, 원본 바이트 범위와 해시를 부여한다.
3. 의미 단위 패커를 만든다. 같은 스냅샷의 인접 섹션을 목표 크기까지 묶고, 하나의 섹션이 상한을 넘을 때만 하위 제목 → 문단 → 줄 → UTF-8 안전 바이트 순서로 재분할한다. 하드 폴백은 계획에 이유와 잘린 단위의 연속 ID를 기록한다.
4. 문맥 봉투를 만든다. 모든 배치에 문서 ID·배치 순서·현재 섹션 범위·전체 제목 지도를 넣고, 현재 원문 앞뒤에는 같은 스냅샷의 인접 범위 제목과 제한된 첫·끝 문장을 추출형 브리지로 제공한다. `CORE` 원문만 근거 가능 영역이며 `DOCUMENT_MAP`·`BEFORE`·`AFTER`는 `context-only`로 표시한다.
5. `coreBytes`, `overlapBytes`, `transmittedBytes`와 각 영역의 위치·해시를 분리하고 커버리지는 `CORE`만으로 계산한다. 봉투 오버헤드를 별도 예산으로 예약하며 완성된 프롬프트가 `maxInputBytesPerCall`을 넘지 않는지 생성 시점과 소비 시점에 모두 확인한다. 제목 지도가 지나치게 크면 현재 위치와 전체 섹션 수를 보존한 채 범위별로 축약하고 축약 건수를 기록한다.
6. 완전 커버리지를 기본값으로 유지한다. 명시적 `--allow-partial`에서는 A/B와 각 문서의 앞·중간·뒤가 한쪽으로 치우치지 않도록 결정론적으로 층화 선택하고, 누락된 섹션 ID·바이트·문서별 커버리지를 `context-plan.json`과 `COVERAGE.md`에 기록한다.
7. `PromptBuilder`는 배치 원문, 위치 정보와 `context-only` 브리지를 구분해 전달한다. 이후 전체 토론 단계에는 기존처럼 검증·커밋된 양쪽 배치 분석 결과만 보이고 원문 전체를 다시 주입하지 않는다.
8. 새 계획 스키마의 필수 필드, 경로·해시·배치 순서·섹션 범위와 완성 팩 해시를 실패 폐쇄한다. 기존 v1 계획은 기존 그래프·프롬프트·해시를 그대로 재개하는 fixture로 보호한다.
9. README와 PRD에는 구현 후 실제 지원 동작만 반영한다. 계획만 존재하는 모델 생성 요약, A/B 의미 대응과 배치별 토론을 현재 기능처럼 설명하지 않는다.

## 슬라이스 11: 공통 메뉴와 LIVE 읽기 경험 2차

### 확정 구현 순서와 안전 경계

1. 모든 목록 선택을 값·표시명·단축키·활성 여부·비활성 이유를 받는 공통 메뉴 선택기로 모은다. `↑/↓` 순환, `Home/End`, `Enter`, `Esc`, 숫자·영문 단축키를 제공한다. VT가 없으면 Windows 콘솔 커서 API를 사용하고, 두 커서 렌더링 방식이 모두 실패할 때만 ANSI 없는 줄 입력으로 한 번 폴백한다.
2. 모델과 분석 깊이의 권장값은 초기 커서 위치에만 사용한다. `Enter` 또는 단축키 확정 전에는 선택값을 만들지 않는다.
3. 기존 프로세스 대기 루프에서 500ms 단위 `PROVIDER_TICK`을 보내고, 경과 시간으로 5셀 heartbeat 프레임을 결정론적으로 계산한다. 별도 타이머·스레드·I/O·공급자 호출·상태 저장·진행률 의미는 추가하지 않는다.
4. header·현재 위치·진단·다음 행동·footer의 필수 행을 먼저 예약하고, 남은 행 예산으로 실행 장벽을 가능한 만큼 늘린다. 충분한 높이에서는 전체 흐름을 표시하고 부족하면 현재 장벽 주변 최소 3개와 `앞 N단계 생략`·`뒤 N단계 생략`을 표시한다.
5. 검증된 최근 완료 후보 최대 3건의 전체 안전 요약과 구조화 변경 집계를 먼저 만든 뒤 남은 높이에 맞춰 배분한다. 높이가 늘 때 표시량이 줄지 않게 하고 최신 선택 항목을 우선하되 나머지 헤더와 의미 있는 본문도 유지한다.
6. 최근 완료 헤더는 단계 그래프 전체 step 번호를 사용한다. 활성 단계가 없으면 `현재 위치`와 별도 `다음 할 일`을 표시하고 대기 상태를 반복하지 않으며, 빨간색은 구조적 오류 행에만 적용한다. capability와 frame writer는 같은 정규화된 viewport 상한을 사용한다.

8. 사용자 표시 경계에서만 모드·단계·상태·중요도·처리·반영 판단과 주요 표 머리글을 일상어로 바꾼다. 내부 ID, 저장 스키마, JSON과 workflow-v1/v2 의미는 유지하고 알 수 없는 값은 원래 값으로 폴백한다.
9. 정확한 `LIVE`, `PARTIAL`, `ROUND`, `APPLY` 확인은 줄 입력 계약으로 분리해 유지한다. 원시 stdout·stderr, 생성 중 텍스트, 전체 문서, 프롬프트·컨텍스트와 모델 응답 원문은 모든 화면에서 계속 금지한다.

슬라이스 착수 당시 커서 메뉴는 물리 `Esc`를 알아들었지만 `LIVE`, `PARTIAL`, `ROUND`, `APPLY`, `Y/N`, 경로·모델명·주관식 입력은 `Read-Host` 계열이라 같은 화면 문법을 보여 주고도 물리 `Esc`를 별도 동작으로 처리하지 못했다. 3차 구현으로 외부 동작 확인, 예/아니요, 질문 계층, 줄 기반 자유 입력, OS 선택기와 진행·완료·오류 경계를 구조화 결과로 옮기고 레거시 어댑터와 직접 입력 중복을 제거했다. 지원 터미널의 실제 호스트 호환성 검증도 완료했다.

이 슬라이스의 목표는 화면마다 키를 개별 해석하는 구조를 없애고, 사용자가 어느 단계에 있든 같은 뜻의 조작이 같은 결과와 복귀 위치를 갖게 하는 것이다. 뒤로가기·취소·중단·잘못된 입력은 AI 요청, 파일 변경, 답변 기록, 작업 생성 같은 부수 효과를 만들지 않아야 한다.

### 공통 조작 문법

| 조작 | 선택·확인 화면 | 자유 입력 화면 | 진행 화면 | 홈 화면 |
|---|---|---|---|---|
| `Enter` | 강조 항목 선택 또는 입력한 확인어 제출 | 현재 값 제출 | 완료 화면에서 작업 메뉴로 복귀 | 강조 항목 선택 |
| `Esc` | 한 화면 위로 즉시 복귀 | 줄 입력에서는 가로채지 않고 입력 전의 명시적 이전 메뉴로 복귀한다 | 상세→개요, 완료→작업 메뉴. 실행 개요에서는 AI를 몰래 중단하지 않고 안전 일시정지 방법을 안내한다 | 종료. 푸터도 `Esc 종료`로 표시한다 |
| `B` | `Esc`와 같은 이전 동작을 제공하는 표시형·줄 입력 폴백 | 유효한 데이터이므로 가로채지 않는다 | 표시형 폴백에서만 이전 | 해당 없음 |
| `Q` | 현재 다단계 흐름을 변경 없이 안정 화면으로 취소 | 유효한 데이터이므로 가로채지 않는다 | 실행 전에는 취소, 실행 중에는 별도의 안전 일시정지 계약을 안내 | 종료 |
| `Ctrl+C` | 사용자 긴급 중단으로 분류하고 화면·커서 상태를 복원 | 사용자 긴급 중단으로 분류 | AI 실행 중에는 기존 체크포인트 보존 중단 계약으로 연결 | 종료 |
| 잘못된 입력 | 오류를 설명하고 같은 화면에 머문다 | 값 검증 오류를 설명하고 다시 입력받는다 | 지원 키를 다시 안내한다 | 같은 화면에 머문다 |

적용 원칙:

1. `Esc`·`B`는 한 단계 이전, `Q`는 현재 흐름 취소, `Ctrl+C`는 긴급 중단으로 서로 다른 뜻을 유지한다. 하위 화면의 `Q=이전`, `0=이전`, 빈 문자열=이전 같은 화면별 별칭은 제거한다. 숫자 `0`은 실제 목록 값에만 쓴다.
2. 자유 텍스트·경로·모델명에서는 `B`와 `Q`를 데이터로 보존한다. 모든 화면에 같은 키를 기계적으로 가로채는 대신 같은 사용자 결과를 제공한다.
3. 정확한 확인어는 대소문자를 구분한 정확한 값과 `Enter`로만 확정한다. 빈 값, 오타, 소문자, 중간 공백은 취소로 오인하지 않고 같은 화면에 남으며, 앞뒤 공백 허용 여부는 PRD에서 하나로 고정한다.
4. Windows 파일·폴더 선택기의 닫기·취소는 오류가 아니라 이전 화면 복귀다. 실제 선택기 실행 실패와 구분한다.
5. 키보드 조작은 애니메이션 없이 즉시 반응한다. 커서 숨김, 대체 화면, `TreatControlCAsInput` 같은 전역 콘솔 상태를 건드린 경우 모든 종료 경로에서 `finally`로 복원한다.
6. 비대화형·리디렉션 환경은 입력을 기다리지 않고 `unavailable`을 반환한다. 이 결과는 확인이나 취소로 위장하지 않는다.

### 공통 입력 계약

입력 함수가 화면별 문자열이나 빈 값 대신 다음 의미를 가진 단일 결과를 반환하도록 한다.

```text
action: submit | back | cancel | interrupt | invalid | unavailable
value:  사용자가 실제로 제출한 값 또는 null
source: key | line | dialog
```

- 공통 키 정규화와 입력 결과 생성은 전용 interaction 계층으로 모은다. `13.Interaction.ps1` 신규 파일 또는 동등한 단일 저수준 어댑터를 후보로 하되, 공개 함수명과 파일명은 구현 전 저장소 로딩 순서를 확인해 확정한다.
- 메뉴, 정확한 확인어, 예/아니요, 자유 입력, OS 선택기는 같은 결과 계약을 사용한다. 기존 호출부는 한 단계씩 옮길 수 있도록 임시 호환 어댑터를 두고 마지막에 제거한다.
- 원시 `ReadKey`와 `Read-Host`는 저수준 입력 어댑터에만 남긴다. 정확한 확인어는 기존 키 capability probe와 테스트용 `KeyReader` seam을 재사용한 작은 편집기로 처리한다.
- 일반 자유 입력은 PowerShell 7 독립 ConsoleHost와 Windows Terminal에서 검증한 줄 입력을 유지한다. 편집기 통합 터미널과 raw editor는 지원·구현 계획에서 제외하고 전역 PSReadLine 설정을 바꾸지 않는다. 선택 메뉴에서 먼저 돌아가기를 제공하며 줄 입력 중 `B/Q`는 데이터로 유지한다.

## 슬라이스 15: 진행 heartbeat와 복합 재개 복구

1. 공급자 프로세스의 `OnTick` closure가 module-private observer 이름을 외부 scope에서 다시 해석하지 않도록 `FunctionInfo` 진입점을 캡처한다.
2. observer·프레임 오류는 공급자 호출과 단계 상태를 깨뜨리지 않고 `PROGRESS_OBSERVER_FAILED` 고정 코드와 안전한 횟수를 한 번만 남긴 뒤 누적 로그로 폴백한다. stdout·stderr, 프롬프트, 문서와 모델 응답은 화면·이벤트·진단에 넣지 않는다.
3. 쟁점 대상은 다른 단계의 정의 중복 검사 집합과 원장까지 포함한 참조 무결성 집합으로 분리한다. 참조 충돌은 산출물 손상으로 오인해 무효화하지 않고 실패 폐쇄한다.
4. 산출물 복구는 없음·해시 불일치·스키마 불일치를 구분하고 해당 단계와 의존 단계만 감사 보존 후 재실행 대상으로 만든다.
5. `attemptCount`는 현재 입력 세대, `totalAttemptCount`는 누적 실제 호출로 분리한다. 사용자 결정으로 세대가 바뀌면 전자만 초기화하며 형식 복구 소진은 terminal `FAILED_STAGE`로 전이한다.
6. `run-20260730-021613-3e022b` 복구는 동일 볼륨 forensic 사본과 작업 복제본을 먼저 만들고, 정규 파일·NTFS ADS·해시·JSON 계약을 검증한 뒤 작업 복제본에 10개 복원·4개 재실행 예정·공급자 0-call을 적용한다. 오프라인 회귀와 복제 검증 통과 후에만 원본에 같은 0-call 복구를 적용하고 `PAUSED_USER`에서 멈춘다.

## 슬라이스 18: LIVE heartbeat 가시성

1. 한 셀 회전 스피너를 5셀 고정 폭의 팽창·수축 heartbeat로 바꾸고 활성 행을 굵은 밝은 노란색으로 강조한다.
2. 공급자 프로세스의 기존 250ms 대기 루프에서 별도 타이머 없이 500ms마다 observer를 호출한다. 경과 시간은 기존 초 단위를 유지하고, 애니메이션 프레임 번호만 500ms 단위로 분리한다.
3. Unicode는 `░░█░░ → ░███░ → █████ → ░███░`, ASCII는 `..#.. → .###. → ##### → .###.` 순환을 사용한다. 두 표현은 항상 5셀 폭이며 진행률 의미를 갖지 않는다.
4. 누적 로그는 기존처럼 heartbeat 이벤트를 출력하지 않는다. observer·writer 오류의 단일 안전 폴백, 공급자 순서, 호출 수, 상태 저장과 `P` 안전 일시정지는 변경하지 않는다.

완료 기준:

- `72×20`, `80×24`, `100×30`, `120×32`에서 heartbeat와 핵심 상태 문구가 잘리지 않고 프레임 경계 안에 남는다.
- 실제 process → provider callback → observer → frame writer seam에서 500ms 프레임 번호와 5셀 pulse 변화를 확인한다.
- PowerShell 파서, 전체 오프라인 회귀, `git diff --check`를 통과하며 실제 공급자 호출과 `resume --live`는 수행하지 않는다.

검증 결과:

- Unicode·ASCII 네 pulse 프레임의 5셀 고정 폭, 활성 행의 굵은 밝은 노란색, 기존 단계 장벽 색상 유지와 process → writer 연결을 합성 검증했다.

## 슬라이스 19: 실패 작업 조회와 제한된 수동 재시도

1. 홈은 `FAILED_STAGE`와 `SOURCE_DRIFT`를 진행·완료·포기 목록에서
   누락하지 않고 `실패한 작업 확인` 전용 목록으로 분리한다.
2. `FAILED_STAGE` 상세 화면은 일반 재개를 계속 숨기고, 실패 단계가
   정확히 하나이며 `RETRY_EXHAUSTED`·`retryable=true`인 경우에만
   `실패 단계 한 번 더 시도 준비`를 제공한다.
3. 정확한 `RETRY` 확인은 실행 잠금과 원자 트랜잭션 안에서 실패 단계만
   `PENDING`, 실행을 `RESUMABLE_ERROR`로 바꾼다. 기존 `attemptCount`,
   `totalAttemptCount`, 마지막 진단과 완료 산출물은 보존한다.
4. 수동 추가 시도는 현재 입력 세대에서 단계당 한 번만 허용한다. 준비 자체의
   공급자 호출은 0건이고 실제 호출은 기존의 별도 `LIVE` 확인을 다시
   통과해야 하며 실패 단계의 수동 추가 호출은 1회다. 후속 정상 단계는
   기존 실행 계획과 LIVE 미리보기의 호출 수를 따른다.
5. 실패 실행도 정확한 `ABANDON`으로 포기·삭제 동선에 넣을 수 있다.
   이 실행을 복원하면 원래 실패 상태로 돌아가며 `PAUSED_USER`를 통한
   재시도 제한 우회를 허용하지 않는다.
6. 메뉴와 고급 CLI `retry-failed`는 같은 준비 함수를 호출한다. CLI의
   비대화형 확인은 `--confirm-retry`를 명시해야 한다.
7. 취소·이전·오타·리디렉션과 재시도 불가능한 실패는 상태·단계·이벤트,

- 혼합 실행에서 진행·완료·실패·포기 카운트와 후보가 각각 정확하다.
- 합성 `FAILED_STAGE`에서 정확한 `RETRY`만 추가 1회를 준비하고
  `PROVIDER_CALL_STARTED`는 증가하지 않는다.
- 준비된 추가 시도의 호출 예산은 1회이며 두 번째 준비는 차단된다.

  `properties`를 `required`로 둔다. 같은 정의에서 provider JSON Schema와 runtime
  validator를 생성하고 공급자 호출 전에 strict subset 정적 검사를 수행한다.
  필수값·형식·허용 개수와 주 결과·부가 결과의 실패 범위도 이 정의에만 둔다.
- `primary`가 유효하면 잘못된 질문·원장 후보만 격리한다. 격리된 질문은 화면에
  노출하지 않되 사용자의 자유 입력 경로는 유지하고, 유효 문서와 이미 사용한
  공급자 호출은 폐기하지 않는다.
- 답변과 공통 전제는 원문 전체가 아니라 현재 단계에 필요한 `userDecisions` 필드만
  투영한다. 답변이 바뀌면 integration, final-validation과 이미 존재하는 조건부
  final-revision만 다시 열고 독립 결과는 보존한다. 재검증이 승인되면 낡은 미완료
  final-revision을 제거한다.
- `decision-application` 복구는 모든 보류 질문의 fingerprint·질문·선택지가 유효한
  기존 답변과 정확히 대응할 때만 허용한다. `RECOVER`는 보류 질문을 비우고 결정에
  영향받는 세 단계만 다시 열어 `PAUSED_USER`로 전이하는 원자적 provider 0-call이다.
- `terminal-recommendation` 복구는 기존 단계가 모두 커밋됐고 미답변 질문이 1~3개이며
  각 권장안 계약이 유효할 때만 허용한다. 사용자가 저장된 권장안을 직접 선택하면
  보존 쟁점을 최종 수정 요구사항으로 투영해 final-revision만 연다. 이 단계의 요청
  계획은 예정 1회·실패 시 추가 0회·최대 1회이며 자동 재시도하지 않는다.
- v3 최종 렌더러는 핵심 문서와 `REVIEW_REPORT.md`를 항상 생성하고 실제 미결정
  질문이 있을 때만 `OPEN_QUESTIONS.md`를 추가한다. v3 단계 결과에서 확인 가능한
  부속 추적 정보만 보고서 절로 통합하며 얇은 자동 코어에는 별도
  `DEBATE_SUMMARY.md`를 만들지 않는다.
- 보고서는 검증·커밋된 단계 상태, 정규 쟁점 원장과 유효 사용자 결정만 사용한다.
  명시적인 채택·거절 또는 반영 위치가 없으면 최종 문서 본문에서 추정하지 않으며,
  원시 stdout/stderr, 프롬프트, 문서 본문, 공급자 출력, 모델 응답 원문과 인증정보를
  포함하지 않는다.
- v1/v2 렌더러의 기존 파일명·본문과 조회·재개 의미는 그대로 유지한다.
