# DuoForge 구현 계획

기준 문서는 `require/PRD.md` v1.6이다. 구현은 기존 실행 의미를 보존하는 테스트 우선 수직 슬라이스로 진행한다.

## 확정 제품 모델

| 화면 모드 | 내부 ID | 입력 | 결과 | 활성 상태 |
|---|---|---|---|---|
| 1. 컨셉으로 공동 문서 만들기 | `shared-document` | brief 또는 컨셉 C | 공동 문서 C' | 활성 |
| 2. 두 문서를 하나로 합의하기 | `document-merge` | 문서 A/B와 각 보조 Markdown | 합의 문서 C와 출처 추적표 | 구현·오프라인 검증 |
| 3. 두 문서를 각각 개선하기 | `dual-document` | 문서 A/B와 각 보조 Markdown | 개선 문서 A'/B' | 구현·오프라인 검증 |
| 4. 두 프로젝트 비교하기 | `dual-project-audit` | 프로젝트 A/B | 비교 결과 | 격리 실패로 비활성 |

- A/B는 공급자나 최초 작성자가 아니라 실행 안의 안정적인 문서 계보다.
- Codex와 Claude는 교체 가능한 검토자·응답자·편집자·합성자·검증자다.
- 단계의 `performedBy`는 감사용 작업 할당이며 문서 소유권을 뜻하지 않는다.
- 기존 내부 ID와 완료·재개 가능한 실행의 의미를 바꾸지 않는다.

## 구현 전 기준선과 역사적 증거

- PowerShell 모듈 버전: `0.8.0`
- 2026-07-28 기준 오프라인 회귀 테스트: 52개 통과
- 기존 공동 문서 E2E `run-20260727-142702-0eeb82`: `workflow-v1 shared-document` 2라운드 13/13 단계 완료
- 기존 독립 문서 E2E `run-20260727-155148-7617d3`: `workflow-v1 dual-document` 2라운드 12/12 단계 완료
- 기존 E2E는 당시 `codex/claude` 역할, `owner-response`, `owned-document-revision`, 기존 파일명과 프롬프트 계약의 역사적 증거다.
- 위 결과와 52개 테스트를 신규 `document-merge` 또는 `workflow-v2 dual-document` 완료 증거로 재해석하지 않는다.
- 기존 인증·질문·결정 변경·추가 근거·대용량 문맥·부분 완료·90분 상한·TUI 진행판 구현은 회귀 기준선으로 보존한다.
- 2026-07-28 문서 모드 확장 구현은 모드 1~3의 2라운드 가짜 공급자 E2E와 68개 오프라인 회귀를 통과했다. 라이브 공급자 검증과는 구분한다.

모든 주요 슬라이스 시작 전과 완료 후 다음 명령을 실행한다.

```powershell
& 'C:\Program Files\PowerShell\7\pwsh.exe' -NoProfile -File '.\tests\Run-Tests.ps1'
```

## 슬라이스 1: 요구사항과 용어 고정

- PRD, 구현 계획과 후속 README를 네 화면 모드로 정렬한다.
- `Codex 문서`, `Claude 문서`, `자신이 소유한 문서`, 신규 `ownerDecisions` 용례를 제거한다.
- 공급자 로그인·모델·의견·단계 실행자를 뜻하는 정상적인 Codex/Claude 용례는 유지한다.
- 완료 게이트: 문서 정적 검색, 요구사항 ID 중복 0건, 전체 회귀 통과.

## 슬라이스 2: 정규 입력 모델과 레거시 어댑터

- 모드 목록과 공개 함수 `ValidateSet`에 `document-merge`를 추가한다.
- 요청 `DocumentA/B`, JSON `inputs.documentA/documentB`, 인벤토리 `roles.documents.A/B`를 도입한다.
- 모드 2·3에 같은 비중첩 폴더, A/B별 보조 Markdown 자동 포함과 출력 경계 검증을 적용한다.
- `--document-a`, `--document-b`, A/B 컨텍스트 옵션을 정규 CLI로 사용한다.
- 기존 `CodexDocument/ClaudeDocument`, `--codex/--claude`와 컨텍스트 옵션은 A/B로 변환하고 사용 중단 예정 경고를 반환한다.
- 신규 매니페스트에는 정규 필드만 기록한다.
- 완료 게이트: 요청·CLI·컨텍스트 중복 방지·경로 경계 단위 테스트와 전체 회귀 통과.

## 슬라이스 3: workflow-v1/v2 호환성

- 신규 실행에 `workflowVersion=workflow-v2`, 신규 프롬프트 계약과 단계 결과 스키마 버전을 기록한다.
- `workflowVersion`이 없는 실행은 `workflow-v1`로 판정한다.
- `workflow-v1 dual-document`의 기존 역할, 단계 그래프, 쟁점 스키마, 파일명과 `duoforge-stage-v2` 프롬프트 계약을 그대로 읽고 재개한다.
- 읽기 경계에서만 레거시 결과를 정규형으로 변환하고 저장된 원본과 완료 산출물을 재작성하지 않는다.
- 단계 그래프 생성, 라운드 추가와 결정 변경 무효화는 `workflowVersion`으로 분기한다.
- 완료 게이트: 기존 실행 조회·재개·선택 무효화 회귀와 기존 파일 해시 불변, 전체 회귀 통과.

## 슬라이스 4: 모드 2 document-merge

- `independent-merge-draft` 두 개가 같은 A/B 스냅샷을 사용하고 서로를 보지 않게 한다.
- 두 후보 완료 장벽 뒤 교차 검토, 응답, 교대 합성과 최종 검증을 실행한다.
- A/B 채택·부분 채택·거부·미결정, 이유와 반영 위치를 구조화한다.
- 최종 C 하나와 `source-trace.md`, 결정·열린 질문·토론 요약을 렌더링한다.
- 완료 게이트: 2라운드 가짜 공급자 E2E, 원본 A/B 해시 불변과 전체 회귀 통과.

## 슬라이스 5: 모드 3 공급자-문서 분리

- 두 공급자가 각각 A/B 모두를 `document-review`하고 쟁점을 `targetDocumentId`로 분류한다.
- 양쪽 검토 뒤 `review-response`, 문서별 `document-revision`, 마지막 편집자가 아닌 공급자의 `document-validation`을 실행한다.
- 편집 담당을 라운드마다 교대하고 A/B 두 개정 완료를 다음 라운드 장벽으로 사용한다.
- 신규 결과는 `document-A-final.md`, `document-B-final.md`와 문서별 채택 기록을 사용한다.
- 신규 스키마는 `sourceDocumentId`, `proposedByProvider`, `performedBy`, `editorialDecisions`를 사용한다.
- 완료 게이트: 2라운드 가짜 공급자 E2E, 공급자-문서 영구 결합 0건과 전체 회귀 통과.

## 슬라이스 6: 메뉴·CLI·진행판과 비노출 경계

- 새 작업 메뉴에 네 모드를 표시하고 모드 4는 비활성 이유를 명확히 보여준다.
- 파일 선택, 최근 경로 역할, 미리보기, 오류와 진행 단계 이름을 A/B 기준으로 변경한다.
- `--plan-only`에 네 모드와 호출 계획을 반영한다.
- 진행 이벤트와 로그는 `runId`, `stepKey`, `workflowVersion`, 공급자, 단계, `targetDocumentId`, 상태, 시각, 공개 오류 코드·범주, 검증된 개수·크기·해시만 허용한다.
- 원문 공급자 출력, stdout·stderr, 프롬프트·문서·컨텍스트 내용, 생성 중 텍스트와 비밀값은 성공·오류·재시도·재개·TUI 폴백의 로그와 이벤트에 기록하지 않는다.
- 필터링된 응답 보존본은 로그·이벤트와 분리된 접근 제한 아티팩트로만 보존한다.
- 완료 게이트: 메뉴·CLI 동등성, 로그·이벤트 금지 내용 0건과 전체 회귀 통과.

## 슬라이스 7: 문서 및 전체 검증

- README 실행 예시, 결과 구조, 도움말과 오류 문구를 갱신한다.
- 모드 1·2·3 각각 2라운드 가짜 공급자 E2E를 실행한다.
- `workflow-v1` 기존 실행의 조회·재개와 파일 의미를 다시 검증한다.
- 라이브 공급자 E2E는 모든 로컬 테스트 통과 뒤 기존 명시적 LIVE 확인 절차로 별도 수행한다.
- 정적 잔여 용어 검색과 원본 해시 불변을 확인한다.
