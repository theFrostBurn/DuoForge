# DuoForge 구현 계획

기준 문서는 `require/PRD.md` v1.8이다. 구현은 기존 실행 의미를 보존하는 테스트 우선 수직 슬라이스로 진행했다.

상태: 문서 모드 확장 Beta 1차, 실행별 안전 진단과 대화형 화면 2차 슬라이스 완료. 모드 1~3의 기존 실제 공급자 E2E는 시점 증거로 보존하며, 2026-07-30 기준 PowerShell 7 오프라인 회귀 121개를 통과했다. 모드 4는 3A 격리 게이트 실패로 계속 비활성이다. 아래의 52·68·87·100·102·118개 수치는 각 슬라이스 완료 당시의 역사적 기준선이다.

## 확정 제품 모델

| 화면 모드 | 내부 ID | 입력 | 결과 | 활성 상태 |
|---|---|---|---|---|
| 1. 컨셉으로 공동 문서 만들기 | `shared-document` | brief 또는 컨셉 C | 공동 문서 C' | 활성 |
| 2. 두 문서를 하나로 합의하기 | `document-merge` | 문서 A/B와 각 보조 Markdown | 합의 문서 C와 출처 추적표 | 실제 E2E 통과 |
| 3. 두 문서를 각각 개선하기 | `dual-document` | 문서 A/B와 각 보조 Markdown | 개선 문서 A'/B' | 실제 E2E 통과 |
| 4. 두 프로젝트 비교하기 | `dual-project-audit` | 프로젝트 A/B | 비교 결과 | 격리 실패로 비활성 |

- A/B는 공급자나 최초 작성자가 아니라 실행 안의 안정적인 문서 계보다.
- Codex와 Claude는 교체 가능한 검토자·응답자·편집자·합성자·검증자다.
- 단계의 `performedBy`는 감사용 작업 할당이며 문서 소유권을 뜻하지 않는다.
- 기존 내부 ID와 완료·재개 가능한 실행의 의미를 바꾸지 않는다.

## 구현 전 기준선과 역사적 증거

- 구현 전 PowerShell 모듈 버전: `0.8.0`; 현재 버전: `0.9.1`
- 2026-07-28 기준 오프라인 회귀 테스트: 52개 통과
- 기존 공동 문서 E2E `run-20260727-142702-0eeb82`: `workflow-v1 shared-document` 2라운드 13/13 단계 완료
- 기존 독립 문서 E2E `run-20260727-155148-7617d3`: `workflow-v1 dual-document` 2라운드 12/12 단계 완료
- 기존 E2E는 당시 `codex/claude` 역할, `owner-response`, `owned-document-revision`, 기존 파일명과 프롬프트 계약의 역사적 증거다.
- 위 결과와 52개 테스트를 신규 `document-merge` 또는 `workflow-v2 dual-document` 완료 증거로 재해석하지 않는다.
- 기존 인증·질문·결정 변경·추가 근거·대용량 문맥·부분 완료·90분 상한·TUI 진행판 구현은 회귀 기준선으로 보존한다.
- 2026-07-28 문서 모드 확장 구현은 모드 1~3의 2라운드 가짜 공급자 E2E와 68개 오프라인 회귀를 통과했다. 라이브 공급자 검증과는 구분한다.
- 2026-07-28 workflow-v2 실제 공급자 실행은 모드 1 `13/13`(Codex 7·Claude 6), 모드 2 `13/13`(7·6), 모드 3 `14/14`(7·7) 단계를 커밋했다. 입력·스냅샷 해시, A/B 계보, 최종 파일과 이벤트·로그 비노출 검증은 통과했다.
- 모드 1·2 라이브 검증은 `AWAITING_USER` 체크포인트로 통과했다. 모드 3은 최초 실행에서 Minor 근거 대기 쟁점이 잘못 차단 상태로 남는 의미 결함을 발견해 중앙 차단 규칙 재계산과 회귀를 적용했고, 수정 후 `run-20260728-095906-127f6d`가 14/14 단계·`AWAITING_USER`로 강화 검증을 통과했다.
- 세 `AWAITING_USER` 실행은 전체 단계 커밋 뒤 질문 카드와 사용자 게이트에 정확히 도달한 실제 공급자 E2E 성공 증거다. 테스트 픽스처의 결정을 임의로 적용해 `COMPLETED`로 바꾸는 재호출은 이 슬라이스의 완료 조건이 아니다.
- 기존 `opus/high` E2E는 아래 검증 요약을 시점 증거로 보존하고 재호출하지 않는다. 향후 새 실제 공급자 E2E가 필요할 때만 테스트 전용 `sonnet/low` 설정, 예상 호출 수와 새로운 정확한 `LIVE` 동의를 사용한다.
- 2026-07-28 A/B 마이그레이션 P0 보강 뒤 오프라인 회귀는 87개 통과다. 추가 근거 원자성과 중단 트랜잭션 복구, 검토 평가/편집 판단/채택 분리, 단계별 계보 행렬, 안정적인 `issueKey`, 공개 요청·CLI 검증, 저장 세대 계약과 workflow-v1 전체 재개 fixture를 포함한다.

## 슬라이스 9: 의미 기반 대용량 문맥 배치

### 확정 범위와 호환 경계

- 1차 목표는 모드 2·3의 대용량 Markdown을 의미 단위로 나누고, 각 배치가 전체 문서에서 차지하는 위치와 앞뒤 연결 문맥을 함께 전달하는 것이다. 모드 1의 기존 대용량 입력도 같은 분할기의 회귀 보호를 받는다.
- 신규 모델 호출, 새 토론 단계와 배치별 교차 비평은 추가하지 않는다. 현재 공급자별 `context-batch-analysis` 1회와 이후 전체 토론 그래프를 유지한다.
- 신규 실행은 `context-plan.schemaVersion=2`, `segmentationPolicy=semantic-markdown-v1`, `envelopePolicy=document-map-extractive-bridge-v1`을 기록한다.
- 기존 `context-plan.schemaVersion=1`, workflow-v1과 초기 workflow-v2 저장 실행은 읽기·조회·재개만 지원하고 분할 파일이나 저장 메타데이터를 재생성·마이그레이션하지 않는다.
- 바이트는 의미 분할의 기준이 아니라 호출 입력의 강제 상한과 최후 폴백으로만 사용한다.

### 테스트 우선 구현 순서

1. 현재 바이트/줄바꿈 분할의 한계를 고정하는 실패 회귀를 추가한다. 제목과 본문, fenced code, 표·목록, 서문·결론이 분리되지 않아야 하는 예시와 모드 2·3 강제 대용량 가짜 공급자 fixture를 먼저 만든다.
2. Markdown 구조 맵을 만든다. ATX/Setext 제목, 제목 경로, 서문, 완결된 문단·목록·표·fenced code를 인식하고 각 원본 스냅샷에 안정적인 섹션 ID, 순서, 원본 바이트 범위와 해시를 부여한다.
3. 의미 단위 패커를 만든다. 같은 스냅샷의 인접 섹션을 목표 크기까지 묶고, 하나의 섹션이 상한을 넘을 때만 하위 제목 → 문단 → 줄 → UTF-8 안전 바이트 순서로 재분할한다. 하드 폴백은 계획에 이유와 잘린 단위의 연속 ID를 기록한다.
